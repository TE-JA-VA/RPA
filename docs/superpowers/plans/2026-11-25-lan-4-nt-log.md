## 1. 스냅숏 '④ 설치 전' - 끝

2026-11-26 09:12 호스트와 NT 를 켰고, 09:16 VM 세션이 스냅숏 '④ 설치 전' 을 떴다 (깨끗한 설치 → ④ 설치 전 순서).

## 2. 시험 빌드 보내기 - 끝

시험 빌드 2026.11.26-1 을 scp 로 `/home/autopilot/incoming/` 에 보냈다. SHA-256 은 위 표의 값이고, 실제 납품 절차를 흉내 내어
이 값을 VM 세션에 따로 알렸다 ('다른 길').

## 3. 설치 (1단계 → 라이선스 → 2단계) - 끝

### 3-1. 1단계 `install.sh install` (VM 세션, root)

```sh
sha256sum -c            # 따로 받은 값과 맞춤 → OK
sudo install -d -m 0700 /root/autopilot-install
# 묶음을 그 폴더로 cp → 그 사본을 tar 로 풂
install.sh install --expect-sha256 23ffe6c1088d4aecdecae82a191b4c147008f6c0cb2563ab35c88770160cf250 \
    --listen 192.168.1.230 --allow 192.168.1.0/24
```

종료 코드 0. 설치 뒤 상태는 아래와 같았다.

| 자리 | 소유자, 권한 |
|---|---|
| `/etc/autopilot` | root:autopilotd 0750 (`ca/` 는 root 0700, `server.json` 0640) |
| `/opt/autopilot` | root 0755, `current` → `releases/2026.11.26-1` |
| `/var/lib/autopilot` | autopilotd 0700 (`seat.key`, `server_request.json` 0600) |
| 서비스 | inactive (라이선스 전) |
| 방화벽 | 넣을 규칙을 보여 주기만 했다 |

### 3-2. 서버 라이선스

요청 파일(server_id `20d6693f082e435fcc6f5b4bc379f4c9`)을 개발 PC 로 가져와 `make_license.py --server` 를 시험 열쇠로 돌렸다.
업체 `c_nt_test`, 자리 10. 만든 `license.json` 의 SHA-256 은 `c704483a…` 이다.

### 3-3. 2단계 `install.sh activate` (VM 세션, root)

- `install.sh activate` 종료 코드 0. 30초 안에 실제로 도는 버전이 2026.11.26-1 로 확인됐고, 타이머 둘(설정 백업, 인증서)이 enable 됐다.
- ufw: `8443,8444/tcp ALLOW from 192.168.1.0/24` (IPv6 규칙은 없다).
- `admin-reset admin --create` - 비밀번호는 사용자가 직접 입력했다. 계정은 mustChange 상태로 만들어졌다.
- `autopilot-server status`: 서버 실행 중, 인증서 남은 날 396일, 첫 백업이 생겼고 메모리는 18.7M.
- 8443 과 8444 는 192.168.1.230 에서만 LISTEN 한다.

## 4. 개발 PC 에서 확인 - 끝

### 4-1. TLS 와 Host 규칙 (`nt_test.py check` 에 옮긴 확인)

- 두 포트 모두 TLS 1.3 (TLS_AES_256_GCM_SHA384).
- 인증서는 CN=AUTOPILOT LAN Server, 발급자 AUTOPILOT LAN CA, SAN IP 192.168.1.230, 용도 serverAuth, 기간 2026-11-25 ~ 2027-12-28.
- `GET /` 에 Host `192.168.1.230:8443` 을 주면 200 로그인 화면. 포트 없는 Host(`192.168.1.230`)와 엉뚱한 Host 는 403
  ('서버 주소로 접속하여 주십시오').
- 응답 머리글에 HSTS, CSP, `X-Frame-Options: DENY` 가 있다.

### 4-2. API 끝까지 (`nt_test.py api` 에 옮긴 흐름)

시험 전용 관리자 `tester` 로 했다. VM 세션이 NT 안에서 무작위 비밀번호로 만들었고, 그 파일은 개발 PC 로 가져온 뒤 NT 에서 shred 했다.

| 확인 | 결과 |
|---|---|
| 첫 로그인 | `session.mustChange` |
| 비밀번호 변경 | 200 |
| 2단계 등록 전 다른 창구 | 403 `auth/must-enroll-mfa` |
| 2단계 등록 시작 | otpauth 주소 받음 |
| 틀린 번호로 켜기 | 거절 |
| 맞는 번호로 켜기 | 켜짐, 복구 번호 8개 |
| 비밀번호만으로 로그인 | 토큰 없이 ticket |
| 두 단계 로그인 | 200 |
| 같은 30초 칸 번호 재사용 | 거절 |
| `POST /api/pcs` | 등록 글(`APE1.`), 주소 `https://192.168.1.230:8444`, 인증 기관 실림 |
| `local_store.enroll` 로 가짜 PC 등록 | 성공 |
| 등록 글의 인증 기관으로 8443, 8444 체인과 이름 확인 | 통과 |
| 에이전트 현황 PATCH → 웹 스트림 | 0.1초 안에 옴 |
| 에이전트 서명 응답 읽기 | 통과 |
| `/api/company` | 등록한 PC 가 보임 |

`admin` 은 그대로 mustChange=True, 2단계 꺼짐이고, 보안 범위는 admin 이다.

시험 스크립트를 처음 돌렸을 때 실패 3건이 나왔지만 서버 문제가 아니었다. 스크립트가 응답 칸 위치(`session` 안)를 잘못 봤고,
`/api/company` 가 비밀번호를 바꾸기 전에도 열려 있는 설계(화면에 업체 이름을 보여 주려고)를 몰랐던 탓이다. 스크립트를 고친 뒤 모두 통과했다.

## NT 로 확인하지 못한 것

- `/var/tmp` 와 `/opt` 가 다른 파일 시스템일 때의 이동 (NT 는 디스크 하나).
- 허용 대역 밖에서 붙어 보기 (NT 는 사무실 망 하나) - 다른 망의 PC 로 사람이 한 번 보거나 업체 환경에서.
- SELinux enforcing 배포판 (NT 는 AppArmor 만).
