# 자동 업데이트 설계 (설치 마법사 3부)

**상태:** 2026-10-07 설계 (사용자와 문답으로 정함). 2026-10-07 구현 (계획 docs/superpowers/plans/2026-10-07-auto-update.md).
**출발:** 설치 마법사 설계(`2026-09-29-installer-design.md`)의 3부 "에이전트가 새 판을 받아 프로그램 파일만 바꾼다".
판 구조(`2026-09-29-release-layout-design.md`)의 `manifest.json`(파일마다 sha256·크기)과 `check_install()` 을 그대로 쓴다.

## 1. 목적 (사용자)

- 새 판이 나올 때마다 업체 PC 를 찾아가 설치하지 않는다. 우리가 판을 내보내고 업체·PC 를 골라 [업데이트] 를 누르면
  그 PC 가 알아서 새 판이 된다.
- **실패하면 반드시 되돌린다** (사용자: "이런거엔 예민해서"). 업데이트 전 상태보다 나빠진 채로 남는 일이 없어야 한다.
- 궁극적으로는 업체 관리자가 직접 누르는 방식(아래 13절). 그 전까지는 우리가 업체마다 하나씩 누른다.

## 2. 정한 것 (문답, 2026-10-07)

| 물음 | 결정 |
|---|---|
| 누가 언제 바꾸나 | **우리 관리 화면(AFTERMARKET_SETUP)에서 업체·PC·판을 골라 [업데이트]**. 업체가 누르는 방식은 나중 (13절) |
| 파일을 둘 곳 | **Firebase Hosting (무료)**, 판 전용 사이트를 따로. 주소를 알면 누구나 받을 수 있다 (자격증명은 안 들어 있다) - 사용자 승인. 나중에 회사 SFTP 로 옮길 수 있게 "받기" 는 한 곳에만 |
| RPA 가 돌고 있으면 | **끝나기를 기다렸다가 바로**. 기다리는 동안 새 실행(예약 포함)은 안 띄운다. 옵저버가 켜져 있어도 끌 때까지 기다린다 |
| 실패하면 | **되돌린다** - 3분 점검 실패, 도중 정전·재부팅 모두. 받기·서명 단계 실패는 아무것도 안 바꾼다 |
| 성공한 뒤에도 되돌리기 | **직전 판 하나를 보관**, 관리 화면 [이전 판으로 되돌리기]. 보관본 100MB 안팎은 업체가 감당 가능 (사용자) |
| 옵저버 "*업데이트가 있습니다. [무시]" | **이번엔 뺀다** - 우리가 누르는 방식이라 업체가 할 일이 없다. 13절에서 넣는다 |
| 바꾸는 방법 | **A. 바뀐 파일만 받아 도우미가 바꾸기** (B 설치 파일 통째로·C 판 폴더 둘은 버림) |
| 호스팅에 남길 판 | **5개**, 그중 **안정본(Stable)** 은 오래돼도 안 지운다. **최신본(Newest)** 은 가장 최근에 내보낸 판에 자동, 안정본은 우리가 지정 |

## 3. 흐름

```
우리 PC                              판 전용 호스팅                 업체 PC
build_release → sandbox_test
publish_release.py ──서명·올리기──▶  manifest·서명·파일들
  (사용자 확인)                       meta/releases (RTDB 목록)
관리 화면 [업데이트] ──명령 update──────────────────────────────▶ 에이전트: 받기·확인 (staging)
                                                                  RPA·옵저버가 쉴 때까지 대기
                                                                  도우미 띄우고 꺼짐
                                                                  도우미: 보관 → 바꾸기 → 에이전트 켜기
                                                                          → 3분 점검 → 성공 / 되돌리기
관리 화면·업체 웹 ◀────────────── live.update (상태) ─────────── 에이전트
```

## 4. 판 내보내기 (우리 PC)

- **판 전용 호스팅 사이트**: 같은 프로젝트(rpa-test-f02e0)에 사이트를 하나 더 만든다 (예: `rpa-test-f02e0-releases`, 무료,
  만드는 것은 사용자 확인 뒤 한 번). 웹 화면 사이트와 나누는 까닭: Hosting 배포는 폴더 통째 덮어쓰기라 웹 화면을 배포할 때
  판 파일이 지워지지 않게. `firebase.json` hosting 을 대상 둘(`web`, `releases`)로 나누고, 지금까지의 `--only hosting` 은
  `--only hosting:web` 이 된다.
- **도구** `tools/publish_release.py <판>`: `D:\AX\배포_<판>` 의 manifest 를 읽어 서명하고, 판 전용 사이트 폴더(우리 PC,
  git 에 안 올림)를 만들어 배포한다. 배포 전에 늘 사용자 확인 (기존 원칙).
  - 파일은 **지문 이름**으로 둔다: `blobs/<sha256>` - 판끼리 같은 파일(파이썬 실행 환경 등)은 한 번만 올라간다.
  - 판마다 `releases/<판>/manifest.json` 과 `releases/<판>/manifest.sig`.
  - 남길 판: 최근 5개 + 안정본. 그 밖의 판과 아무 판도 쓰지 않는 blob 은 폴더에서 빼고 배포한다 (Hosting 이 지운다).
- **판 목록**은 Realtime DB `meta/releases` 에 둔다 (관리 화면이 Admin SDK 로 읽고 쓴다, 안정본 지정이 배포 없이 바로 된다):
  `{ list: { "<판 키>": { version, published_at, bytes, memo } }, stable: "<판>", newest: "<판>" }`.
  판 키는 `2026_10_07-4` 처럼 점을 뺀 꼴 (RTDB 키에 `.` 못 씀). 내보내기 도구는 `node setup.js release-add …` 를 불러 적는다.
- **크기 (실측 2026.10.07-4)**: exe 셋 116MB·파이썬 42MB·나머지 1MB 남짓. exe 는 빌드마다 지문이 바뀌어 **보통 판은
  120MB 안팎**을 받는다 → 무료 하루 360MB 로 하루 PC 2~3대. 파이썬 코드만 바뀐 판은 `build_release.py --exes-from` 으로
  exe 를 다시 쓰면 몇 MB.

## 5. 서명

- **ed25519 열쇠 한 쌍.** 비밀 열쇠는 우리 PC `firebase/admin/` 에만 (서비스 계정 키와 같은 자리, git 에 안 올림, 대화·기록에
  내용을 남기지 않음). 공개 열쇠는 프로그램 코드에 박는다. 사본은 사용자가 USB 등에 직접 보관한다.
- 서명 대상은 `manifest.json` 바이트 그대로. PC 는 서명을 확인한 manifest 의 sha256·크기로 받은 파일 하나하나를 확인한다.
- 업체 PC 의 파이썬에는 `cryptography` 가 없다 → **표준 라이브러리만 쓰는 ed25519 (RFC 8032 참조 구현)** 를 한 파일로 넣는다
  (`update_sign.py`, 서명·확인 둘 다, 새 부품 안 깜). 확인 한 번은 1초 안쪽이면 된다.
- 비밀 열쇠를 잃으면 새 판을 서명할 수 없다 → 새 공개 열쇠가 든 판을 모든 PC 에 직접 설치해야 한다 (13절 아님, 운영 주의).

## 6. PC - 에이전트

- **명령 둘** (`KNOWN_TYPES`): `update {version}` · `rollback`. 받자마자 검사만 하고 "업데이트를 예약했습니다" 로 명령을 끝낸다
  (명령 유효 시간과 상관없이 오래 기다릴 수 있게). 진행은 `live.update` 로 올린다.
  - 거절: 이미 업데이트 중 / 같은 판 / `rollback` 인데 보관본 없음 / 판 구조가 `mixed`·`error` (먼저 손으로 고쳐야).
- **받기** (`update\staging\<판>\`): `releases/<판>/manifest.json`·`.sig` → 서명 확인 → 지금 판 manifest 와 견줘 sha256 이
  다르거나 새로 생긴 파일만 `blobs/<sha256>` 에서 받는다 → 받은 파일마다 sha256·크기 확인. 하나라도 틀리면 staging 을 지우고
  `failed` (아무것도 안 바꿈). 받는 곳 주소는 코드 상수 하나 (`UPDATE_BASE_URL`) - SFTP 로 옮길 때 받기 함수만 바꾼다.
- **디스크**: 받을 양 + 보관할 양(바뀔 옛 파일 합) + 여유 200MB 보다 모자라면 시작 전 `failed`.
- **기다리기**: `update\state.json` 에 `waiting` 을 적는다. 이 동안 rpa_dashboard 는 새 실행을 띄우지 않는다
  (단추·예약·반복 모두, 까닭 "업데이트 중이라 잠시 실행할 수 없습니다"). RPA 와 옵저버가 모두 쉬면 다음 단계.
- **넘기기**: 도우미와 파이썬 실행 환경을 `update\runner\` 로 복사하고, 일회용 예약 작업 `\AFTER MARKET\RPA Update`
  (로그온 때 도우미 `--recover`)을 걸고, 도우미를 띄운 뒤 에이전트는 끝낸다 (도우미는 에이전트 작업 묶음 밖으로 띄운다 -
  `schtasks /End` 에 같이 죽지 않게).
- **새 에이전트가 켜질 때**: `update\state.json` 이 `applying` 이면 판 점검(`check_install`) 을 하고 Firebase 첫 로그인에 성공하면
  `update\alive.json {version, state, at}` 를 적는다 (도우미의 3분 점검이 이것을 본다).

## 7. 도우미 (`update_helper.py`)

프로그램 폴더 밖 `C:\ProgramData\AFTER MARKET\RPA\update\runner\` 에서 복사한 파이썬으로 돈다 - 프로그램 폴더의 파이썬이 반쯤
바뀌어도 돈다. ProgramData 폴더 권한(관리자·SYSTEM)을 그대로 물려받는다.

1. `state.json` 을 `applying {target, from, started_at}` 로 (이 표시가 있는 동안은 "끝나지 않은 업데이트").
2. 에이전트 작업 끝내기 (`schtasks /End`), 에이전트 뮤텍스가 풀릴 때까지 기다린다.
3. **보관**: 바뀔 옛 파일과 치울 옛 파일(옛 manifest 에만 있는 것)을 `update\backup\<옛 판>\` 로 **옮기고** 옛 manifest 도 둔다.
   이전 보관본은 이때 지운다 (보관은 늘 직전 판 하나).
4. **바꾸기**: staging 의 새 파일을 제자리로 옮기고 새 manifest 를 놓는다. 제거 목록의 판 번호
   (`HKLM\…\Uninstall\{C3F7A2B4-5E81-4D2A-9B6C-7A1E0F3D8B52}_is1` 의 `DisplayVersion`)도 고친다.
5. 새 판의 `rpa_settings.py --after-install --no-window` (예약 작업 다시 등록 + 에이전트 켜기 - 조용한 설치와 같은 길).
6. **3분 점검**: `alive.json` 의 version 이 새 판이고 state 가 `ok` 이면 성공 → `state.json` `done`, 일회용 예약 작업 지움.
   3분 안에 안 오면 (에이전트가 안 켜짐·판 점검 mixed·로그인 실패 모두) **되돌리기**.
7. **되돌리기**: 에이전트 끝내기 → 새 판이 넣은 파일을 치우고 보관본을 제자리로 → 옛 manifest·판 번호 → `--after-install` →
   다시 3분 점검 (옛 판). `state.json` `rolled_back {reason}`. 이때 보관본은 실패한 새 판이 아니라 그대로 옛 판 - 되돌린 뒤
   [업데이트] 를 다시 누를 수 있다.
8. **`--recover`** (정전·재부팅 뒤 로그온): `state.json` 이 `applying` 이면 되돌리기부터 한다. `done`/`rolled_back` 이면
   일회용 예약 작업만 지운다.

- **[이전 판으로 되돌리기]** (`rollback` 명령): 보관본을 "새 판" 으로 보고 같은 1~7 을 돈다 - 받기 없이. 성공하면 보관본은
  방금까지 쓰던 판이 된다 (앞으로 다시 갈 수 있다).
- 도우미의 기록은 `update\업데이트_기록.txt` (한국어, 단계마다 한 줄).

## 8. 우리 관리 화면 (AFTERMARKET_SETUP)

- 업체 상세의 PC 줄마다: `pc_a · 판 2026.10.07-4 (안정본) · 업데이트됨 10/7 14:03` - 판 번호는 `live/…/version`, 상태는
  `live/…/update`, 표시는 `meta/releases`.
- **[업데이트]**: 올라가 있는 판 고르기 (판 옆 `(안정본)`·`(최신본)`, 처음 골라진 것은 안정본) → 확인 창
  "c_demo / pc_a 를 2026.10.07-5 로 바꿉니다. RPA 가 끝나면 바로 바뀝니다." → 명령 `update`.
- **[이전 판으로 되돌리기 (2026.10.07-4)]**: 보관본이 있을 때만 (`live/…/update.backup`).
- 진행 중(`waiting`·`applying`)이면 두 단추 잠금.
- **판 목록 칸**: 올라가 있는 판 5개 + [안정본으로 지정]. 누른 일은 모두 `관리_기록.txt`.

## 9. 업체 웹 화면 (보기만)

- 판 번호 옆 작은 글: `업데이트 대기 중` / `바꾸는 중` / `업데이트됨 (10/7 14:03)` / `업데이트 실패 - 옛 판으로 되돌림`
  (까닭은 마우스 글).
- `waiting`·`applying` 이면 실행 단추를 잠그고 단추 아래 "업데이트 중이라 잠시 실행할 수 없습니다".

## 10. 데이터·규칙

- `apps/rpa/live/{cid}/{pcId}/update`: `{ state: waiting|downloading|applying|done|failed|rolled_back, target, from, at, reason,
  backup }` (에이전트가 올린다, 웹·관리 화면이 읽는다).
- `meta/releases`: 4절. 관리 화면(Admin SDK)만 쓴다. 업체 계정은 읽지도 않는다 (13절 때 연다).
- 명령 규칙(`database.rules.json` 의 type 목록)에는 `update`·`rollback` 을 **넣지 않는다** → 업체 계정은 못 넣고 Admin SDK 만
  넣는다. 에이전트도 명령의 `by` 가 관리 화면 표시인지 한 번 더 본다.

## 11. 오류 처리

| 상황 | 결과 |
|---|---|
| 서명·지문 틀림, 받기 끊김, 디스크 부족 | 아무것도 안 바꿈, `failed (까닭)` |
| RPA 가 몇 시간 돎 | 계속 `waiting` (웹에 보임). 관리 화면에서 취소는 안 만든다 - 끝나면 바뀐다 |
| 새 에이전트가 3분 안에 정상 안 올림 | 되돌리기 → `rolled_back` |
| 바꾼 직후 인터넷이 끊겨 첫 로그인 실패 | 새 판이 멀쩡해도 되돌린다 (안전한 쪽). 다시 [업데이트] 하면 된다 |
| 바꾸는 도중 정전·재부팅 | 로그온 때 `--recover` 가 되돌리기 |
| 되돌리기도 실패 (디스크 가득 등) | `state.json` 에 남기고 기록. 사용자가 설치 파일로 직접 다시 설치 (대비책) |
| 판 구조가 이미 `mixed` | 명령 거절 - 손으로 고친 PC 를 자동으로 덮지 않는다 |

## 12. 시험

- **단위 (임시 폴더, 가짜 Program Files·가짜 호스팅 = 로컬 http 서버)**: 서명 맞음·틀림·파일 하나 지문 다름, 바뀐 파일만 고르기,
  디스크 부족, 이미 업데이트 중, 대기 중 실행 거절, 도우미를 바꾸는 도중 죽이고 `--recover`, 3분 점검 실패 → 되돌리기,
  `rollback`, 보관은 늘 하나.
- **에뮬레이터**: 관리 화면 [업데이트]·[되돌리기]·[안정본으로 지정]·잠금·상태 글, 업체 웹 상태 글·실행 단추 잠금,
  업체 계정의 `update` 명령은 규칙이 거절.
- **샌드박스 (깨끗한 윈도우)**: 판 A 설치 → 판 B 를 샌드박스 안 가짜 호스팅에 내보내 업데이트 → 성공 → [되돌리기] → A →
  망가뜨린 판 C 업데이트 → 3분 점검 실패 → 되돌림 → 바꾸는 도중 도우미를 강제로 끄고 로그온 → 되돌림.
- **실제 운영**: 개발 PC 에는 깔지 않는다. 실제 호스팅을 거친 첫 업데이트는 사용자가 시험 업체 PC 한 대로.

## 13. 나중에

- **업체 관리자가 직접** (궁극 목표): 업체 웹에 "업데이트가 있습니다 [지금 업데이트]" (안정본만), 규칙에 `update` 열기,
  옵저버 오른쪽 위 "*업데이트가 있습니다. [무시]" (켤 때·30분마다, [무시]는 다시 열 때까지 - 2026-10-02 결정).
- 회사 SFTP 서버로 옮기기 (받기 함수만).
- 코드 서명 인증서 (윈도우 Authenticode) - 이번 서명과 별개.
- 업데이트 취소 단추, 여러 PC 한꺼번에.
