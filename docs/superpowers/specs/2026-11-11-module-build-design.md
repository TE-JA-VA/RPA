# 조각 컴파일 빌드 설계

작성: 2026-11-11 · 상태: 사용자 검토 대기 (구현자 검토 반영함)

## 1. 무엇을, 왜

- **문제:** 빌드가 느리다. exe 하나에 약 170초, 셋이면 약 8분 30초다. 공통 파일(`rpa_status.py` 등) 하나만 고쳐도 셋을 다 새로 만든다.
- **원인:** Nuitka onefile 은 빌드할 때마다 우리 코드와 남의 라이브러리(Playwright·pywinauto·comtypes 등)를 통째로 다시 컴파일한다.
- **검토했다가 버린 길:**
  - Rust 포팅 - 사용자: 빌드 속도만 아니면 모험할 까닭이 없다.
  - 소스(`.py`) 그대로 배포 - 사용자: 소스는 절대 보여 주고 싶지 않다 (미래 주력 상품).
  - 시험 코드 제외·Nuitka 4.3.4 - 2026-11-11 실측에서 시간이 줄지 않았다 (4.3.4 는 더 느려 4.2.2 로 되돌림).
- **고른 길:** 우리 파일을 하나씩 따로 컴파일(`.pyd`)하고, 남의 라이브러리는 컴파일하지 않고 그대로 싣는다. 고친 파일만 다시 컴파일한다.

## 2. 목표 / 하지 않을 것 / 실패로 볼 것

**목표**
- 파일 하나를 고친 뒤 빌드(컴파일)가 30초 안쪽.
- 그때 PC 가 받는 업데이트가 수 MB 안쪽.
- 업체 PC 에 우리 소스(`.py`)가 지금보다 더 보이지 않는다.
- 사용자가 보는 것은 그대로: 프로그램 이름·아이콘·시작 메뉴·대시보드 단추·`Run_All.bat`·설정 파일.

**하지 않을 것**
- 프로그램 동작·화면 변경.
- Python·Nuitka·라이브러리 버전 올리기.
- 에이전트 등 지금 `.py` 로 나가는 파일의 컴파일 (2단계로 미룸 - 8절).

**실패로 볼 것**
- 옛 방식으로 돌아갈 수 없게 되는 것.
- 전환 업데이트가 PC 에서 실패했는데 되돌려지지 않는 것.
- 소스가 지금보다 더 드러나는 것.

## 3. 실험으로 확인한 것 (2026-11-11, 임시 폴더)

ACTOR(`web_runner.py`)의 우리 파일 12개를 `python -m nuitka --module` 로 하나씩 컴파일했다.

| 항목 | 결과 |
|---|---|
| 컴파일 | 12개 모두 성공, 파일당 9~25초 (2,500줄 파일이 25초), 차례로 전부 173초 |
| 크기 | 12개 합쳐 12MB (파일당 약 1MB) |
| 실행 | 조각 + 얇은 시작 파일로 `--check` 가 끝 줄까지 통과 |
| 경로 | `__compiled__` 가 있고 `containing_dir` = 조각이 놓인 폴더. 실험은 조각을 프로그램 폴더에 바로 둬서 `program_dir()`·`packaged()` 가 exe 때와 같았다. `app\` 에 두면 한 단계 어긋난다 (4절) |

확인하지 않은 것 (실험 때): PROCESS·옵저버, 실제 사이트·ERPia 실행, 내장 Python + 실은 라이브러리 구성, 샌드박스 설치·업데이트.

## 4. 바뀐 뒤의 배포본 모양

```
{설치 폴더}\
  ERPia_RPA.exe            얇은 시작 파일 (아이콘, 콘솔)        ← 이름 그대로
  Prepare_RPA.exe          얇은 시작 파일 (아이콘, 콘솔)        ← 이름 그대로
  Prepare_Observer.exe     얇은 시작 파일 (아이콘, 창 프로그램)  ← 이름 그대로
  app\                     우리 조각: run_routine.*.pyd, web_runner.*.pyd, rpa_status.*.pyd …
  python\                  내장 Python (지금 그대로)
  lib\                    남의 라이브러리: playwright, pywinauto, comtypes, pywin32, greenlet, pyee, PIL …
  playwright\node.exe      지금 그대로 한 벌
  rpa_status.py, rpa_dashboard.py, firebase\agent\… 등  지금 그대로 (1단계에서는 안 건드림)
```

- **얇은 시작 파일:** 내장 Python 을 불러 `app\` 의 시작 모듈 `main()` 을 실행하는 작은 exe. 바뀌는 일이 거의 없어 한 번 만들면 계속 같은 파일이다. 만드는 방법은 구현자가 정한다 (후보: 에이전트·감독처럼 내장 `python.exe` 사본에 아이콘을 넣고 인자를 고정, 또는 작은 C 시작 파일). 조건: 작업 관리자·작업 표시줄에 지금 이름과 아이콘으로 보이고, 인자(`--check`, `--all` 등)와 종료 코드가 그대로 전달된다.
- **시작 모듈:** `run_routine`·`web_runner`·`rpa_observer` 는 지금 `if __name__ == "__main__":` 안에서 예외 처리를 한다. 이 부분을 함수(예: `run_main()`)로 옮겨 시작 파일이 부를 수 있게 한다. 소스로 직접 돌릴 때의 동작은 그대로 둔다.
- **시작 파일은 작은 C 프로그램이다 (검토 2026-11-11):** `python.exe` 사본은 `python314.dll` 이 `python\` 에 있어 프로그램 폴더에서 못 켜지고 인자도 고정하지 못한다. 같은 프로세스 안에서 Python 을 실행해야 한다 - '실행 중' 판정이 프로세스 이름을 보고 (`rpa_settings.py:46,126`), 옵저버의 관리자 재실행이 `sys.argv[0]` 을 쓴다 (`rpa_observer.py:1952`).
- **경로 코드를 고친다:** 조각이 `app\` 에 있으면 `containing_dir` 이 `{설치 폴더}pp` 이다. `rpa_status.program_dir()` (262줄)과 `web_replay` 의 node 찾기 (54줄)가 프로그램 폴더를 가리키게 고친다. 같은 코드가 옛 onefile 빌드에서도 맞아야 한다.
- **공통 모듈 두 벌:** `rpa_status` 등은 프로그램 폴더의 `.py` (에이전트·대시보드용)와 `app\` 의 `.pyd` 두 벌이 된다. 시작 파일은 `app\` 을 먼저 찾게 한다 - 아니면 `packaged()` 가 거짓이 된다. 2단계에서 한 벌로 합친다.
- **라이브러리 자리 (Claude 판단):** `python\Lib\site-packages` 가 아니라 따로 `lib\` 폴더. `python\` 은 지금 버전 목록 밖이고 업데이트 때 통째로 복사되는 곳이라 섞지 않는다. 내장 Python 은 `._pth` 가 없는 전체 Python 이라 시작 파일이 `site.addsitedir` 로 더하면 pywin32 의 `.pth` 도 동작한다.
- **라이브러리 크기:** 실을 것은 약 40MB (node.exe 88MB 는 이미 따로 싣고 있다).

## 5. 빌드

- `tools/build_release.py` 에 조각 방식을 더한다. 파일마다 재료 지문(소스 내용 + Nuitka·Python 버전 + 옵션)을 보관 폴더에 두고, 같으면 보관한 `.pyd` 를 그대로 쓴다. 지금의 exe 보관(`build/exe_cache`)과 같은 생각이다.
- 한 파일의 지문에는 그 파일만 들어간다. 다른 우리 파일이 바뀌어도 다시 만들지 않는다 (조각은 서로를 실행 때 import 한다).
- `.pyd` 는 판 목록(`manifest.json`)에 파일로 들어간다. 그래서 자동 업데이트·파일 변조 감지는 고칠 것 없이 바뀐 조각만 받고 검사한다.
- 라이브러리(파일 약 1,000개)는 묶음 파일 하나로 보낸다 (11절).
- 링크 옵션 `LDFLAGS=-march=x86_64` 는 조각에도 준다 (AVX-512 없는 PC 에서 죽던 문제).
- 조각 여러 개를 동시에 컴파일하는 것은 하지 않는다. exe 동시 빌드에서 원인 모를 고장이 있었다 (TODO '동시 빌드 보류').

- **패키지 목록:** `D:\AX\checkpoint_onefile_2026-11-11_pip_freeze.txt` (그때의 `.venv` 패키지 버전).
- **빌드 도구 안에서도:** 옛 onefile 빌드 코드를 지우지 않는다. `build_release.py --onefile` 로 지금과 같은 exe 셋을 만든다. `build/exe_cache` 도 지우지 않는다.
- **기본값:** 조각 방식이 샌드박스와 실기 한 대에서 확인되기 전까지 기본은 옛 방식이다. 확인 뒤 사용자가 말하면 기본을 바꾼다.
- **체크포인트의 뜻:** 태그는 '빌드 방식'의 기준점이다. 작업 폴더의 다른 미커밋 작업(다른 세션)은 그 세션이 커밋한다. 옛 방식 빌드는 태그로 돌아가지 않고도 `--onefile` 로 최신 코드에서 만든다.
- **PC 쪽:** 조각 버전에서 옛 버전으로 되돌리기는 지금의 [이전 버전으로 되돌리기]와 옛 버전 [업데이트]가 그대로 한다. 샌드박스 전환 시험(`--from`)으로 양쪽 방향을 확인한다.

## 8. 순서

**1단계 (이 설계)**
1. ACTOR 를 조각 방식으로 - 빌드·`--check`·샌드박스.
2. 옵저버·PROCESS 를 같은 방식으로.
3. 샌드박스: 새 설치, 옛 버전 → 조각 버전 업데이트, 되돌리기.
4. 실기 한 대에서 실제 수집·ERPia 처리. (사용자 확인) 올리는 법 (Claude 판단): 조각 버전을 업데이트 호스팅에 내보내되 안정본은 그대로 두고 메모에 '시험용' 을 적는다. 사용자가 시험 PC 에만 [업데이트]를 보낸다 - 옛 → 조각 업데이트를 실기에서 해 보기 위해서다.
5. 사용자가 말하면 기본을 조각 방식으로 바꾸고 버전을 내보낸다.

**2단계 (따로 정함)**
- 지금 소스로 나가는 파일(에이전트·대시보드·설정 창·업데이트)도 조각으로. 업데이트 도우미는 프로그램 폴더 밖 사본으로 돌아 따로 살펴야 한다.

## 9. 구현자에게 맡기는 것

- 얇은 시작 파일을 만드는 방법 (4절 조건 안에서).
- `app\` 폴더 이름과 조각 보관 폴더 모양.
- 실을 라이브러리 목록을 뽑는 방법 (지금 exe 가 싣는 것과 같아야 한다).
- 시험: 지금 있는 `tests/test_build_release.py`·샌드박스 검사에 조각 방식 항목을 더한다.

## 10. 정한 사람

- **사용자:** 빌드 속도가 목적, 소스는 보이지 않게, Rust 는 안 함, 옛 방식으로 빌드할 수 있는 체크포인트.
- **Claude 판단 (검토 대상):** 조각 + 라이브러리 그대로 싣기, 프로그램 이름·자리 유지, 태그·`--onefile` 두 겹 체크포인트, 기본값은 확인 뒤에 바꿈, 에이전트 쪽은 2단계, 동시 컴파일 안 함.

## 11. 라이브러리를 이미 깔린 PC 에 보내는 법 (사용자 결정 2026-11-11: 묶음 파일 하나)

- 걸림: 옛 버전의 업데이트 코드는 파일을 하나씩, 다시 시도 없이 받는다 (`rpa_update.py:203-212`). 라이브러리 약 1,000개를 목록에 넣으면 하나만 실패해도 전환 업데이트 전체가 실패한다.
- 정한 것: 라이브러리를 묶음 파일 하나로 만들어 판 목록에 넣는다. 새 버전의 설치 마무리(`rpa_settings --after-install`, 업데이트 뒤에도 돈다)가 `lib\` 에 푼다. 새 설치(설치 파일)도 같은 길로 푼다.
