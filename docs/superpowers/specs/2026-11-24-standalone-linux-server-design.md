# 오토파일럿 스탠드얼론 사내 서버(리눅스) 설계

- 작성 2026-11-24, 사용자 요청 "업체 서버가 리눅스다. Firebase 에서 웹 대시보드로 설정을 만지고 실행 명령을 내리듯, 사내 서버가 있고 거기에 연결된 웹 대시보드와 윈도우 에이전트들이 있는 것"
- 앞 설계: `2026-11-23-standalone-local-server-design.md` (아래 '어제 설계'). 이 문서는 그 12절 "나중에 (가)로 갈 때" 를 푼 것이다. 여기서 (나)는 PC 한 대 스탠드얼론, (가)는 사내 서버를 뜻한다.
- 브랜치 `StandAlone` (새 저장소는 만들지 않는다 - 사용자 2026-11-24). 이 문서로 코드를 고치지 않는다. 계획은 14절 차례대로 따로 쓴다.
- 2026-11-24 검토 뒤 사용자 답을 반영했다 (2단계 인증과 로그인 이력, 리버스 프록시 뒤에 설 자리, PC 대수, 새 PC 에만 설치, NT 를 새 PC 에 두기). 어느 업체에 들어갈지는 아직 정해지지 않았으므로 이 문서는 업체를 정하지 않고 쓴다.

## 1. 왜 만드나

(나)는 PC 마다 로컬 서버가 있어 그 PC 앞에 앉아야만 현황을 보고 명령을 내릴 수 있다. 업체는 사내에 리눅스 서버를 두고, 일반 버전에서 하던 것처럼 **한 화면에서 여러 PC 를 보고 시키기**를 원한다. 다만 Firebase 는 여전히 쓸 수 없고 서버도 회사 밖으로 나가지 않는다.
그래서 (나)의 로컬 서버를 사내 리눅스 서버 한 대로 옮기고, 각 PC 의 에이전트가 그 서버에 붙게 한다. PROCESS, ACTOR, 옵저버, 예약 실행은 지금처럼 각 PC 안에서 돈다.

## 2. 정한 것

| 항목 | 결정 | 누가 |
|---|---|---|
| 서버 | 업체 사내 리눅스 서버 한 대. 웹 대시보드와 윈도우 에이전트가 이 서버에 붙는다 | 사용자 2026-11-24 |
| 업데이트 | **가) 완전 폐쇄 먼저.** 서버는 밖으로 나가지 않는다. 관리자가 새 버전을 파일로 받아 대시보드에 올리면 서버가 사내 PC 에 나눠 준다. 고객사가 허용하면 나중에 '나) 우리 업데이트 주소에서 서명된 새 버전만 받는 통로' 를 얹는다 (받아서 나눠 주는 부분은 같게) | 사용자 2026-11-24 |
| 시험 | 실제 업체 서버에 넣기 전에 리눅스 VM "NT" 에서 똑같이 시험한다. NT 는 개발 PC 가 아닌 **새 PC** 의 VMware 에 둔다. 우선 사내에서만 접속 | 팀장님 지시, 사용자 2026-11-24 |
| PC 대수 | 확정은 2대, 예상은 최대 5대. 설계 목표는 여유를 두어 **10대** | 사용자 2026-11-24 (목표 숫자는 Claude 판단) |
| 붙을 PC | **새 PC 에만 설치한다.** 일반 버전이나 (나)가 깔린 PC 를 바꿔 끼우는 단위는 만들지 않는다 | 사용자 2026-11-24 |
| 서버 구조 | 업체 서버의 정확한 모양(프록시, WAF, WEB/WAS/DB 분리)은 아직 모른다. 먼저 VM 리눅스에서 서버를 만들고 그 아래에 붙일 수 있는지 확인한다. 그래서 리버스 프록시 뒤에 설 자리를 설계에 넣는다 (6.3) | 사용자 2026-11-24 |
| 웹 인증 | 2단계 인증(인터넷 없이 도는 인증 앱 방식)과 로그인 이력 화면을 만든다. 업체 관리자가 켜고 끌 수 있게 한다 ("없더라도 만들어 둔 다음에 안 쓰면 된다") | 사용자 2026-11-24 (기본값은 Claude 판단 - 6.6) |
| 어제 정한 것 | AI 어시스트 완전 제외, 1회 구매에 토큰 무제한, 바깥 연결은 쇼핑몰·ERPia·메일뿐, 휴대폰 인증번호는 사내 와이파이로, 브랜치 `StandAlone` | 사용자 2026-11-23 |
| 복사 막기 | 어제는 'PC 에 묶는다' 였다. (가)에서는 라이선스를 서버에 묶고 PC 수를 정하며, 각 PC 는 서버가 준 자리 증명서(그 PC 번호에 묶임)로 켜진다 (6.8) | Claude 판단 (어제 설계 12절 "라이선스를 'PC 수' 로" 를 따름) |
| 만드는 방식 | 지금 로컬 서버 코드를 넓혀 리눅스에 싣는다 (4.2 의 A) | Claude 판단, 사용자 2026-11-24 "A안 그대로" |
| 서버에 싣는 파이썬 | 서버 설치 파일에 리눅스용 내장 파이썬을 함께 넣는다 (4.3) | Claude 판단, 12절에서 확인 |

## 3. 목표 · 하지 않을 것 · 실패로 볼 것

**목표**
- 사내망의 브라우저에서 업체 웹을 열어 여러 PC 의 현황을 보고, 설정을 바꾸고, 실행·중단 명령을 내린다. 화면은 지금 업체 웹 그대로다.
- 서버와 PC 모두 쇼핑몰·ERPia·메일 말고는 회사 밖으로 연결하지 않는다. 서버는 그 셋에도 연결하지 않는다 (서버가 스스로 여는 연결은 없다).
- 새 버전은 관리자가 올린 파일 하나로 모든 PC 에 들어가고, PC 는 지금 일반 버전의 업데이트처럼 스스로 바꾸고 문제가 있으면 되돌린다.
- 일반 버전, (나), (가)가 같은 코드에서 나온다 (어제 설계 4절 A 유지).
- 서버가 꺼져 있어도 각 PC 의 예약 실행은 계속 돈다. 그동안의 실행 기록은 PC 에 쌓였다가 서버가 살아나면 올라간다 (에이전트의 밀린 기록 큐 그대로).
- 고객사 보안 검토에서 흔히 묻는 웹 인증 다섯 가지(2단계 인증, 첫 로그인 비밀번호 변경 강제, 로그인 잠금, 미사용 자동 로그아웃, 로그인 이력)를 사내 서버 웹이 모두 갖춘다.

**하지 않을 것 (이번 범위 밖)**
- 나) 통로. 얹을 자리만 정해 둔다 (6.7).
- 일반 버전이나 (나)가 깔린 PC 를 사내 서버용으로 바꾸기 (새 PC 에만 설치).
- 윈도우 서버, 서버 여러 대(이중화), 여러 업체를 한 서버에 두기, DB 를 다른 장비에 두기 (업체가 요구하면 12절 1번에서 다시 본다).
- AI 어시스트, 토큰, 총괄 화면, 우리 쪽 관리 화면. 우리는 이 서버를 원격으로 보지 않는다.
- 아이폰 단축어 (어제와 같다).
- 프리셋 옮기기는 맨 뒤 차례로 미룬다 (14절 ⑪).

**실패로 볼 것 (돌아가도 실패)**
- 서버나 PC 가 Firebase·Google·Anthropic·우리 사이트로 연결을 시도한다 (실패해도 시도 자체가 실패).
- 대시보드나 에이전트 창구가 사내망 밖에서 열린다.
- 어떤 PC 의 열쇠로 다른 PC 의 명령을 받거나, 다른 PC 의 현황·기록을 쓴다.
- 일반 버전이나 (나)의 동작이 바뀐다 (두 버전의 시험·샌드박스가 그대로 통과해야 한다).
- 구매하지 않은 서버나 PC 에서 켜진다.
- 서명이 없거나 틀린 업데이트 파일이 서버에 보관되거나 PC 에 설치된다.
- 2단계 인증이 필수인 계정이 번호 없이 로그인된다. 또는 프록시가 아닌 곳에서 보낸 주소 머리글을 믿어 잠금과 로그인 이력의 주소가 속는다.

## 4. 만드는 방법 (고른 것과 버린 것)

### 4.1 업데이트 통로 (사용자가 고름)
가) 완전 폐쇄를 먼저 만든다. 나)는 '서버가 새 버전을 들이는 길' 하나만 다르므로, 들어온 파일을 확인하고 보관하고 나눠 주는 부분을 가)에서 완성해 두면 나)는 들이는 길 하나를 더하는 일이 된다.

### 4.2 만드는 방식 (Claude 판단 - A 추천, 사용자 2026-11-24 "A안 그대로")

| 안 | 모양 | 장점 | 단점 |
|---|---|---|---|
| **A. 지금 로컬 서버를 넓혀 리눅스에 싣기 (고름)** | `local_server.py`, `local_web.py`, `local_phone.py` 에 '배치 설정'(듣는 주소, TLS, PC 등록부)을 더하고, 리눅스에 필요한 것(경로와 권한, systemd, 설치 스크립트)만 얇게 새로 쓴다 | 서버 검사와 그 시험(로컬 서버, 웹, 휴대폰 시험)을 그대로 쓴다. (나)와 (가)가 한 코드라 고침이 같이 간다. 표준 라이브러리뿐이라 서버에 따로 깔 것이 없다 | 표준 `http.server` 로 TLS 와 여러 PC 를 감당해야 한다 (PC 10대 목표라 무리가 없다고 본다 - 6.5, 10절 부하 시험으로 확인). 윈도우 전용 코드를 갈라야 한다 (13절) |
| B. 서버만 새로 쓰기 | 웹 프레임워크와 DB 서버로 다시 만든다 (서버 옮기기 메모의 Supabase 안 포함) | TLS 처리와 동시 접속, DB 가 이미 검증된 것들이다. WEB/WAS/DB 를 나누라는 조건에 맞추기 쉽다 | 검사 규칙과 시험을 다시 만든다. (나)와 서버가 두 벌이 된다. 인터넷이 없는 서버에 패키지를 여럿 깔아야 한다. 보안 자료가 말한 약속을 두 구현이 따로 지켜야 한다 |
| C. A 를 컨테이너로 싣기 | A 의 서버를 이미지로 만들어 docker 나 podman 으로 돌린다 | 배포판 차이를 덜 탄다 | 업체 서버에 컨테이너 실행기가 있어야 한다 (없으면 인터넷 없이 깔기 어렵다). 업체 보안 검토 대상이 늘고, 서버 번호와 방화벽과 폴더 권한을 한 겹 더 거쳐 다뤄야 한다 |

A 를 고른 까닭: 사용자가 원하는 것은 '지금 것을 사내 서버로' 이고, 어제 설계가 이미 서버와 에이전트를 다른 프로세스로 갈라 두었다. B 는 같은 약속을 두 번 만들고, C 는 업체 서버에 조건을 하나 더 건다. 업체 서버 구조를 모르는 채 시작하므로 A 에 '프록시 뒤에 설 자리' 를 넣어 두고 NT 에서 먼저 확인한다 (6.3). C 는 업체가 컨테이너를 원하면 A 의 서버 설치 파일을 그대로 이미지에 넣어 나중에 더할 수 있다.

### 4.3 리눅스 서버에 파이썬을 싣는 방법 (Claude 판단 - ① 추천)

| 안 | 모양 | 장점 | 단점 |
|---|---|---|---|
| **① 내장 파이썬을 함께 싣기 (추천)** | 서버 설치 파일 안에 리눅스용 이식형 CPython(python-build-standalone)을 넣는다. 우리 개발 PC 에서 받아 지문을 확인해 싣는다 | 서버에 아무것도 깔지 않는다. 인터넷이 필요 없다. 배포판마다 다른 파이썬·OpenSSL 버전을 타지 않는다 (윈도우 내장 파이썬과 같은 3.14 계열) | 설치 파일이 수십 MB 커진다. 업체가 '바깥에서 온 실행 파일' 을 서버에 올리는 것을 허용해야 한다. glibc 2.17 이상인 x86_64 만 된다 |
| ② 서버에 깔린 파이썬 쓰기 | 배포판의 python3 로 돈다 | 업체가 관리하는 실행 파일만 쓴다 | 배포판마다 버전이 다르다 (3.6 인 곳도 있다). 서버 코드를 가장 낮은 버전에 맞춰 써야 하고 시험할 조합이 는다 |
| ③ 리눅스에서 컴파일한 실행 파일 | Nuitka 로 서버를 한 파일로 만든다 | 파이썬이 보이지 않고 고치기 어렵다 | 리눅스 빌드 환경과 빌드 시험이 새로 든다 |

①로 시작한다. ③은 서버 쪽 복사 막기를 보강할 때 다시 본다 (6.8).

## 5. 전체 모양

```
┌──────────────────────── 업체 사내망 (서버는 밖으로 나가지 않는다) ────────────────────────┐
│                                                                                          │
│ [사내 PC 의 브라우저] ──https 8443 (로그인)──────────▶ ┌──────────────────────────────┐  │
│        (업체가 원하면 이 사이에 업체의 프록시)         │ 사내 서버 (리눅스, systemd)    │  │
│ [업무 PC 1 … N]                                       │  local_server · local_web      │  │
│   에이전트 ──https 8444 (PC 마다 다른 열쇠)─────────▶ │  - 계정·세션, PC 등록부         │  │
│   ACTOR·옵저버 ──https 8444 (인증번호 중계 열쇠)────▶ │  - 현황·명령·실행 기록          │  │
│   PROCESS · 예약 실행 (그 PC 안에서 그대로)           │  - 업데이트 보관·나눠 주기      │  │
│      │                                                │  - 서버 라이선스 (자리 수)      │  │
│      │                                                └───────────┬──────────────────┘  │
│ [휴대폰 앱] ──사내 와이파이 https 8782 (인증번호 창구만)──────────┘                     │
└──────│───────────────────────────────────────────────────────────────────────────────────┘
       ▼ 쇼핑몰·ERPia·메일 (PC 만, 업체가 허용한 것)

[공급사(우리)] ··· 파일로만 건넨다: 서버 설치 파일, PC 업데이트 파일, 라이선스 → 업체 관리자가 사내로 들여와 올린다
```

- 포트 셋은 저마다 자기 창구만 답한다. 8443 은 브라우저, 8444 는 에이전트와 인증번호 중계, 8782 는 휴대폰. 방화벽에서 포트마다 들어올 수 있는 대역을 따로 줄 수 있다.
- 각 PC 는 로컬 서버를 띄우지 않는다. 에이전트, ACTOR 실행, 옵저버가 `local_store` 클라이언트로 사내 서버에 직접 붙는다 (어제 설계 5절과 같은 세 프로세스).

## 6. 부분별 설계

### 6.1 버전 종류와 연결 방식 ((나)와의 관계)
- (나)와 (가)는 둘 다 남는다. 버전 종류(`edition`)는 지금처럼 `cloud` / `standalone` 둘이고, 스탠드얼론 안에서 **연결 방식**이 '단독'(나) 과 '사내 서버'(가) 로 갈린다. 새 버전 종류를 만들지 않는 까닭은 스탠드얼론이면 꺼지는 것(AI, 토큰, Firebase 주소, 업데이트 사이트)이 (가)에서도 똑같이 꺼져야 하기 때문이다. (Claude 판단)
- 연결 방식은 화면의 스위치가 아니라 **서명된 증명**으로 정해진다. PC 번호 라이선스(`license.json`)가 있으면 단독이고, 서버가 준 자리 증명서(6.8)가 있으면 사내 서버다. 둘 다 있거나 둘 다 없으면 켜지지 않는다 (어제 검토의 fail-closed 원칙).
- 윈도우 설치 파일은 스탠드얼론용 하나를 같이 쓴다. 설치 마법사에서 '이 PC 단독으로 사용'(라이선스 파일 고르기) 과 '사내 서버에 연결'(등록 파일 고르기) 가운데 하나를 고른다. 일반 버전이 깔린 PC 에서는 어제처럼 설치를 멈추고 안내한다.
- 단독이면 감독(`background.py`)이 지금처럼 로컬 서버를 띄운다. 사내 서버면 로컬 서버를 띄우지 않고 에이전트만 지킨다.
- 서버 코드는 같은 파일이다. 단독은 '127.0.0.1, http, PC 하나, 열쇠 하나' 라는 배치 설정으로, 사내 서버는 '사내 주소, TLS, PC 등록부' 라는 배치 설정으로 돈다. 단독의 배치 설정 값은 지금 동작과 한 글자도 다르지 않아야 하고, (나) 시험과 샌드박스가 그것을 지킨다.
- 업체 웹도 같은 파일이다 (`data-local.js`). 서버가 PC 를 둘 이상 알려 주면 화면에 PC 고르기가 저절로 나온다 (6.6).

### 6.2 서버 프로그램 (리눅스)
- **서버 설치 파일** `AUTOPILOT_Server_<버전>_linux-x86_64.tar.gz` 와 그 서명 파일. 안에는 내장 파이썬, 서버 코드, 업체 웹 파일, 버전 목록(`manifest.json`)과 서명, `install.sh` 가 들어 있다. `tools/build_release.py --edition standalone` 이 윈도우 설치 파일, PC 업데이트 파일과 함께 같은 버전 번호로 만든다.
- **폴더** (Claude 판단)

| 자리 | 내용 | 소유자·권한 |
|---|---|---|
| `/opt/autopilot/releases/<버전>/`, `/opt/autopilot/current` | 프로그램. `current` 는 지금 버전을 가리키는 링크 | root, 서비스 계정은 읽기만 |
| `/etc/autopilot/` | `server.json`(주소, 포트, 허용 대역, 믿을 프록시), `license.json`, 인증 기관 열쇠 | root, 서비스 계정은 설정과 라이선스만 읽기 (인증 기관 열쇠는 root 만) |
| `/var/lib/autopilot/` | 저장소, 실행 기록과 로그인 이력 DB, 계정, PC 등록부, 휴대폰 표, 열쇠, 서버 인증서, 올린 업데이트, 백업 | 서비스 계정 `autopilot` 만 (폴더 700, 파일 600) |
| `/var/log/autopilot/` | `server.log`, `audit.log` (10MB 다섯 개까지 돌려 쓴다) | 서비스 계정만 |

- **서비스**: `autopilot.service` 가 로그인할 수 없는 전용 계정 `autopilot` 으로 돈다. 죽으면 5초 뒤 다시 켜고, 라이선스 문제(종료 코드 2)로 끝나면 다시 켜지 않는다. systemd 의 보호 설정으로 프로그램 폴더를 읽기 전용으로 보이게 하고(`ProtectSystem=strict`, 쓸 수 있는 곳은 자료·기록 폴더뿐), 새 권한을 얻지 못하게 하며(`NoNewPrivileges`), 되는 배포판에서는 서비스가 사내 대역 밖으로 패킷을 보내지 못하게 한다(`IPAddressDeny=any` 와 허용 대역). 서비스 계정이 프로그램 폴더를 쓸 수 없으므로 웹 창구가 뚫려도 서버 코드를 바꿔 끼우지 못한다.
- **기록**: 어제와 같이 열쇠, 비밀번호, 세션 토큰, 인증번호, 2단계 인증의 비밀 값과 번호는 싣지 않는다. 명령, 계정과 PC 와 휴대폰을 바꾼 일, 보안 설정을 바꾼 일, 업데이트 올리기는 보낸 쪽 주소와 함께 `audit.log` 에 남긴다. 로그인은 화면으로 볼 수 있게 DB 에 따로 남긴다 (6.6). 파일 이름은 리눅스 관리자가 다루기 쉽게 영문으로 한다.
- **백업**: `autopilot-server backup` 이 자료 폴더를 하나의 파일로 만든다 (DB 는 SQLite 백업 기능으로, 올린 업데이트는 뺀다). `autopilot-backup.timer` 가 하루 한 번 돌려 7개를 남긴다. 백업 파일에는 열쇠, 계정 해시, 2단계 인증 비밀 값이 들어 있어 서비스 계정만 읽는다. 다른 장비로 옮겨 보관하는 것은 업체 몫이고 설치 안내서에 적는다. 복구는 서비스를 멈추고 `autopilot-server restore <파일>`. 다른 장비에 복구하면 서버 번호가 달라 라이선스를 다시 받아야 한다.
- **서버를 다시 켜면**: 웹 세션은 모두 풀려 다시 로그인한다 (지금과 같다). 현황은 메모리에만 있으므로 에이전트가 다시 붙으며 새로 올린다. 대기 중이던 명령은 파일에 남아 있다가 만료 시간(실행·중단 90초, 나머지 600초)이 지나면 닫힌다. 열려 있던 인증번호 요청은 사라지고 ACTOR 가 다시 연다. 에이전트와 화면의 구독은 지금처럼 물러서며 다시 붙는다.
- **관리 명령** `autopilot-server`: `request`(서버 번호 요청 파일 만들기), `status`, `cert`(인증서를 보거나 다시 만들거나 업체 인증서를 넣기), `admin-reset`(관리자 비밀번호나 2단계 인증을 다시 정하기 - (나)의 설정 창 단추 자리, 서버의 root 만), `backup`, `restore`, `verify <파일>`(서명 확인).

### 6.3 사내망 HTTPS · 포트 · 방화벽 · 프록시
- 세 포트 모두 TLS 1.2 이상만 받는다. http 포트는 열지 않는다. TLS 악수는 연결마다 일하는 스레드에서 5초 안에 끝내게 한다 (`local_phone.PhoneServer` 가 이미 쓰는 방식).
- **브라우저가 믿을 인증서** (8443)

| 안 | 모양 | 브라우저 경고 | 비고 |
|---|---|---|---|
| ① 업체 사내 인증 기관이 발급 | 서버가 요청서(CSR)를 만들고 업체 IT 가 발급해 넣는다 | 없음 (PC 가 이미 그 기관을 믿는다) | 업체에 사내 인증 기관이 있을 때 가장 좋다. 우리가 PC 에 넣는 것이 없다 |
| **② 서버가 만든 '오토파일럿 사내 인증 기관' (기본, 추천)** | 설치할 때 서버가 인증 기관과 서버 인증서를 만든다. 업무 PC 는 서버에 등록할 때 설정 창이 그 인증 기관을 윈도우 신뢰 저장소에 넣는다. 에이전트가 없는 PC 는 업체 IT 가 인증 기관 파일을 나눠 준다 | 넣은 PC 는 없음 | 인증 기관에 이름 제한을 걸어 이 서버 이름·주소의 인증서만 만들 수 있게 한다. 인증 기관 열쇠는 root 만 읽고 서비스 계정은 못 읽는다. 서버 인증서는 약 1년짜리로 root 타이머가 미리 다시 만든다 |
| ③ 자체 서명 인증서와 브라우저 경고 | 경고 화면에서 지문을 눈으로 견주고 넘어간다 | 매번 | 경고를 넘기는 습관이 들고 가로채기를 구별하기 어렵다. NT 첫 시험에서만 쓴다 |

  기본은 ②, 업체에 사내 인증 기관이 있으면 8443 만 ①로 바꿔 끼운다. 어느 쪽이든 PC 의 신뢰 저장소에 무엇이 들어가는지는 보안 자료에 밝힌다. 이름 제한을 브라우저가 실제로 지키는지는 NT 에서 확인한다.
- **에이전트가 서버를 믿는 방법** (8444): 에이전트는 윈도우 신뢰 저장소를 보지 않는다. 등록 때 받은 '오토파일럿 사내 인증 기관' 하나만 믿는 TLS 설정으로 붙고 서버 이름까지 확인한다. 8443 의 인증서를 업체 것으로 바꿔도 8444 는 늘 우리 인증 기관의 인증서를 쓰므로 에이전트는 영향을 받지 않는다. 서버 인증서가 해마다 바뀌어도 인증 기관이 같아 다시 등록하지 않는다. 회사 프록시는 지금처럼 따르지 않는다.
- **휴대폰** (8782): 지금처럼 10년짜리 자체 서명 인증서와 QR 의 지문으로 확인한다 (7절). 웹 인증서와 따로라 웹 쪽을 바꿔도 휴대폰을 다시 짝짓지 않는다.
- **사내망 밖에서 열리지 않게** 세 겹으로 막는다. ① 서버는 `server.json` 에 적힌 사내 주소에만 듣고, 그 주소가 사설 대역이 아니면 켜지지 않는다. ② 허용 대역 밖에서 온 연결은 TLS 악수 전에 닫는다 (휴대폰 포트가 이미 하는 검사를 세 포트에 다 쓴다). ③ `install.sh` 가 firewalld 나 ufw 에 넣을 규칙(포트 셋, 들어올 수 있는 대역)을 보여 주고 관리자가 승인하면 넣는다. 서비스 자신은 방화벽을 바꿀 권한이 없다. 공유기나 방화벽 장비에서 이 서버로 포트를 넘겨 주는 설정은 우리가 막을 수 없으므로 설치 안내서에 '하지 말 것' 으로 적는다.
- 포트 번호(8443, 8444, 8782)는 `server.json` 에서 바꿀 수 있다. 1024 아래 포트를 쓰지 않아 서비스에 특권이 필요 없다. (Claude 판단)

**리버스 프록시 뒤에 설 자리** (업체 서버 구조를 아직 모른다 - 12절 1번. 기본은 프록시 없이 직접 붙는 모양이고, 아래는 설정으로 켜는 자리다)
- **믿을 프록시 주소**: `server.json` 의 `trusted_proxies` 목록. 기본은 비어 있고, 그때는 `X-Forwarded-For` 와 `X-Forwarded-Proto` 를 아예 읽지 않는다 (누구나 지어 보낼 수 있는 값이다).
- **그때만 믿기**: 목록에 있는 주소에서 온 연결에 한해 `X-Forwarded-For` 를 오른쪽부터 읽어, 믿을 프록시가 아닌 첫 주소를 '보낸 쪽 주소' 로 쓴다. 이 주소가 허용 대역 검사, 로그인 잠금, 로그인 이력, 세션 주소에 쓰인다. 이 자리가 없으면 모든 사용자가 프록시 주소 하나로 보여, 한 사람이 비밀번호를 틀리면 모두가 잠긴다. 프록시가 아닌 곳에서 온 연결의 그 머리글은 버린다. `proxy_only` 를 켜면 8443 은 프록시 주소에서 온 연결만 받는다.
- **TLS 를 누가 끝내나**: 두 모양을 받는다. (ㄱ) 프록시가 브라우저의 TLS 를 받고 서버까지 다시 TLS 로 잇는다. 서버는 지금 모양 그대로이고 프록시가 우리 인증 기관을 믿게 하면 된다. 이쪽을 추천한다. (ㄴ) 프록시가 TLS 를 끝내고 서버에는 평문으로 넘긴다. 프록시가 서버와 같은 장비에 있고 서버가 127.0.0.1 에만 들을 때만 켤 수 있게 한다 (장비 사이에 평문 구간을 만들지 않는다). 이때 `X-Forwarded-Proto` 가 https 가 아니면 거절하고, Host 와 Origin 은 프록시가 내건 이름으로 검사한다.
- **프록시가 지켜 줘야 하는 것**: 현황 구독은 오래 열린 연결이다. 응답을 모아 두지 않고 흘려보내야 하고, 30초 넘는 조용한 시간을 끊지 않아야 한다 (서버는 30초마다 살아 있다는 줄을 보낸다). 업데이트 파일 올리기는 수백 MB 를 받아야 한다. 설치 안내서에 nginx 설정 예시를 싣는다.
- **프록시 뒤에 서는 것은 8443 뿐**이다. 8444 와 8782 는 직접 붙는 것이 기본이다. 꼭 프록시나 WAF 를 거쳐야 한다면 TCP 를 그대로 넘기는 방식만 된다. TLS 를 끝내는 장비를 거치면 에이전트가 믿는 인증 기관과 휴대폰의 지문 확인이 맞지 않게 되고, 요청 서명 머리글과 오래 열린 구독을 그 장비가 건드리지 않아야 한다. 업체가 그 모양을 요구하면 그때 다시 설계한다.
- **WEB/WAS/DB 분리**: 업체의 WEB 서버(프록시) 뒤에 우리 서버가 WAS 로 서는 모양까지는 위의 자리로 된다. DB 를 다른 장비에 두라는 조건이면 A 의 파일 저장소로는 맞출 수 없다. 저장소 층(`Store`, `Runs`)은 HTTP 를 모르게 갈라져 있어 그 층만 DB 서버용으로 바꿔 끼우는 길이 있고, 그때는 계획을 따로 쓴다.
- **확인**: NT 에서 nginx 를 8443 앞에 세워 (ㄱ)과 (ㄴ) 두 모양으로 로그인, 현황 구독, 업데이트 파일 올리기, 주소 읽기를 본다 (10절, 14절 ④와 ⑨).

### 6.4 PC 등록과 에이전트 인증
- **PC 마다 열쇠가 다르다.** 지금은 그 PC 의 `agent.key`·`relay.key` 한 쌍이 서버의 전부지만, 사내 서버는 PC 등록부에 PC 마다 한 쌍을 둔다.
- **등록 절차**
  1. 관리자가 업체 웹 환경설정의 'PC' 카드에서 [PC 추가] 를 누르고 PC 이름을 적는다. 자리가 남아 있어야 한다 (6.8).
  2. 서버가 **등록 파일**을 내준다. 서버 주소와 포트, 그 PC 의 번호, 한 번만 쓰는 등록 열쇠, 인증 기관 인증서가 들어 있고 10분 동안 유효하다. 같은 내용을 붙여 넣을 수 있는 한 줄 글로도 보여 준다.
  3. 그 PC 의 '오토파일럿 설정' 창(또는 설치 마법사)에서 등록 파일을 고른다. PC 는 파일의 인증 기관으로 서버를 확인한 뒤에만 등록 요청을 보낸다.
  4. PC 가 난수를 보태 열쇠를 만든다 (휴대폰 짝짓기와 같은 방식이라 등록 파일만 주운 사람은 열쇠를 만들 수 없다). 서버는 PC 번호, 윈도우 PC 번호(MachineGuid), 컴퓨터 이름을 등록부에 적고 자리 증명서와 서버 라이선스 사본을 돌려준다.
  5. PC 는 열쇠 둘, 서버 주소, 인증 기관, 자리 증명서를 설정 폴더에 관리자만 읽게 저장한다 (지금 `lock_key_files` 그대로).
- **요청 서명**은 지금 HMAC 방식을 넓힌다. 서명하는 글에 PC 번호를 넣고(`ap2`), 서버는 PC 번호와 역할로 등록부에서 열쇠를 찾아 확인한다. 응답과 구독 이벤트에도 지금처럼 그 PC 의 열쇠로 서명을 붙인다. TLS 가 있어도 서명을 남기는 까닭은 PC 를 확인하는 수단이 이것뿐이고, 같은 요청 다시 보내기를 막기 때문이다. 단독은 지금의 `ap1` 을 그대로 쓴다.
- **자기 자리만**: 서버는 서명으로 확인한 PC 번호가 자리 이름의 PC 번호와 같을 때만 현황 쓰기, 명령 읽기와 상태 옮기기, 기록 올리기를 받는다 (지금은 라이선스의 PC 번호와 견준다 - `local_server.allowed`). 인증번호 요청의 `pcId` 도 같은 값이어야 한다.
- **시계**: 닫힌 망의 PC 는 시계가 틀릴 수 있다. 서버는 시각이 2분 넘게 다르면 서명이 맞을 때 서버 시각을 서명해 알려 주고, 클라이언트는 그 차이를 더해 한 번 다시 보낸다 (휴대폰 창구의 `clock` 응답과 같은 방식).
- **사용 중지와 지우기**: 사용 중지하면 그 PC 의 요청에 서명된 '중지됨' 으로 답한다. 에이전트는 '사람이 고쳐야 하는 멈춤' 으로 끝나고 설정 창에 까닭이 보인다. 지우면 열쇠와 현황·명령 자리를 없애고 자리를 돌려준다. 실행 기록은 PC 이름과 함께 남긴다. 지운 PC 의 에이전트는 '지워짐' 응답을 받으면 자기 자리 증명서를 지운다.
- 등록 창구와 에이전트 창구에는 주소마다 동시 연결 수, 분당 요청 수, 서명 틀림 횟수 제한을 건다 (휴대폰 포트의 제한을 같이 쓴다).

### 6.5 저장소와 서버 검사
- 자리 이름은 어제 그대로다 (`apps/rpa/live/<cid>/<pc>`, `commands`, `runs`). PC 번호 자리에 여러 값이 들어올 뿐이다. 단독의 PC 번호는 MachineGuid 이고 사내 서버의 PC 번호는 서버가 붙인 짧은 번호(`pc_01` 꼴)다. (Claude 판단)
- 새 자리는 PC 등록부(`pcs.json`, 열쇠 포함, 서비스 계정만), 올린 업데이트 목록, 로그인 이력(DB), 그리고 맨 뒤 차례의 프리셋 옮기기 자리다. 업체 정책(모듈, 기능, 한도)은 지금처럼 라이선스에서 읽어 `meta/companies/<cid>/apps/rpa` 로 답한다.
- 서버 검사는 어제와 같다. 관리자만 명령을 만들고, 명령 인자는 만들 때만 정해지며 엑셀 비밀번호 칸은 거부한다. 에이전트는 상태를 한 칸씩만 옮긴다.
- 쇼핑몰·ERPia 비밀번호와 엑셀 비밀번호는 지금처럼 PC 에만 있고 서버로 오지 않는다.
- **저장소는 JSON 파일 하나 그대로 둔다** (Claude 판단). PC 가 예상 5대, 목표 10대이면 나무 크기는 1MB 안팎이고 쓰기는 초당 몇 번이다. 쓰기 한 번에 나무를 복사하고 파일을 다시 쓰는 지금 방식으로도 한 코어의 일부만 쓴다. 저장소를 PC 별로 나누거나 DB 로 옮기면 (나)와 같이 쓰는 코드와 그 시험을 건드리게 되어 얻는 것보다 잃는 것이 크다. 손질은 하나만 한다. 메모리에만 두는 자리(현황, 인증번호)만 바뀐 쓰기에는 파일을 다시 쓰지 않는다. 현황은 PC 수만큼 가장 자주 오는 쓰기인데 파일 내용은 그대로이기 때문이다 (13절 2번). 다시 볼 때는 10절의 부하 기준을 넘지 못할 때와 PC 가 수십 대로 늘 때다.
- 연결 상한은 PC 한 대 기준(동시 연결 64, 웹 구독 16)에서 PC 10대와 브라우저 여럿에 맞게 올리고, 에이전트 구독과 웹 구독을 따로 센다.
- 실행 기록과 로그인 이력은 보관 기간이 지나면 서버가 하루 한 번 지운다 (기간은 12절).

### 6.6 업체 웹
- **로그인과 세션의 바탕은 지금 그대로다.** 계정은 서버에 pbkdf2 해시로 두고, 세션 토큰은 쿠키가 아니라 탭 저장소와 `Authorization` 머리글로 다닌다. 쿠키가 없으므로 다른 사이트의 화면이 사용자의 로그인을 빌려 요청을 보낼 수 없다.
- **웹 인증 다섯 가지.** 고객사 보안 검토에서 요구받은 적이 있는 항목이고 이 서버에도 걸릴 가능성이 높다. 걸리지 않더라도 만들어 두고 끄면 되므로 다 갖춘다 (사용자 2026-11-24).

| 항목 | 지금 로컬 서버 | 사내 서버 |
|---|---|---|
| 2단계 인증 | 없음 | 새로 만든다 (아래) |
| 첫 로그인 비밀번호 변경 강제 | 있음 (`must_change`) | 그대로 |
| 로그인 잠금 | 아이디마다 5번 틀리면 60초 | 아이디와 주소 둘 다 세고, 잇따르면 길어진다 (아래) |
| 미사용 자동 로그아웃 | 30분, 로그인 뒤 12시간 상한 | 그대로 |
| 로그인 이력 | 서버 기록 파일에 한 줄 | DB 에 남기고 화면으로 보인다 (아래) |

**2단계 인증**
- **방식**은 시간 기반 일회용 번호(TOTP, RFC 6238)다. 휴대폰의 인증 앱(Google Authenticator, Microsoft Authenticator 같은 것)이 인터넷 없이 30초마다 6자리 번호를 만들고, 서버도 같은 계산만 하므로 바깥 연결이 없다. 표준 라이브러리로 만든다.
- **켜고 끄기**: 환경설정에 '보안' 카드를 두고 관리자가 '끔', '관리자 계정만 필수', '모든 계정 필수' 가운데 고른다. **기본값은 '관리자 계정만 필수'** 로 추천한다 (Claude 판단). 까닭은 셋이다. 관리자 계정은 사내망 어디서나 실행 명령, 계정과 PC 관리, 업데이트 올리기를 할 수 있어 비밀번호 하나에 맡기기 어렵다. 유저는 보기만 하므로 필수로 하면 불편이 얻는 것보다 크다. 그리고 보안 설정은 꺼진 채 나가면 그대로 꺼진 채 쓰이기 쉽고, 켜진 채 나가면 끄는 일이 업체의 결정으로 기록에 남는다. 범위를 줄이거나 끌 때는 비밀번호와 지금 번호를 다시 넣게 하고 `audit.log` 에 남긴다.
- **등록**: 필수인 계정이 아직 등록하지 않았으면 로그인한 뒤 등록 화면만 쓸 수 있다 (비밀번호 변경 강제와 같은 방식 - 서버가 다른 창구를 막는다). 화면에 QR 과 손으로 넣을 글을 보이고 (QR 그리기는 휴대폰 짝짓기에 쓰는 `qr.js` 그대로), 앱의 번호를 한 번 넣어 맞아야 켜진다. 그때 한 번만 쓰는 복구 번호 8개를 한 번 보여 준다. 첫 로그인의 순서는 비밀번호 바꾸기, 그다음 2단계 등록이다. 설치 직후의 첫 관리자도 같은 길을 탄다.
- **로그인**: 아이디와 비밀번호가 맞으면 세션 대신 5분짜리 표를 주고, 번호까지 맞아야 세션을 준다. 번호는 앞뒤 한 칸(30초)까지 받고, 한 번 쓴 번호는 다시 받지 않는다. 틀린 번호는 로그인 잠금에 같이 센다 (6자리 번호를 찍어 맞히지 못하게).
- **계정 저장 모양**: 계정 파일을 버전 2로 올려 계정마다 2단계 비밀 값, 마지막으로 받은 시간 칸, 복구 번호의 해시, 켠 시각을 더한다. 비밀 값은 서버가 번호를 계산해야 해서 해시로 둘 수 없다. 서비스 계정만 읽는 자료 폴더에 두고 백업에도 들어간다. 어느 응답과 기록에도 싣지 않는다. 비밀번호를 바꾸거나 다시 정할 때 이 칸들이 지워지지 않게 한다 (13절 12번).
- **복구**: 휴대폰을 잃었으면 복구 번호로 로그인해 다시 등록한다. 복구 번호도 없으면 다른 관리자가 그 계정의 2단계를 풀어 주고, 그 계정은 다음 로그인에 다시 등록한다. 관리자가 한 명뿐인데 그 관리자가 비밀번호나 2단계를 잃었으면 서버의 root 가 `autopilot-server admin-reset` 으로 다시 정한다. 웹에는 '잊었을 때' 길을 두지 않는다 (메일도 문자도 보낼 수 없는 망이고, 웹에 그런 길이 있으면 그것이 가장 약한 곳이 된다).
- **시계**: 서버 시계가 1분 넘게 틀리면 번호가 맞지 않는다. 로그인 화면과 '서버' 카드에 서버 시각을 보이고, 설치 안내서에 서버 시계 맞추기를 적는다.

**로그인 이력**
- **남기는 것**: 로그인 성공, 실패(비밀번호가 틀림, 2단계 번호가 틀림), 잠김, 사용 중지된 계정의 시도, 로그아웃과 자동 로그아웃, 2단계 설정을 바꾼 일. 한 건마다 시각, 아이디, 보낸 쪽 주소, 브라우저 종류를 적는다. 등록되지 않은 아이디는 지금처럼 글자를 남기지 않는다 (아이디 칸에 비밀번호를 잘못 친 경우 때문이다).
- **화면**: 누구나 '내 계정' 에서 자기 최근 로그인을 보고, 로그인 직후 '마지막 로그인' 의 시각과 주소를 본다. 관리자는 환경설정의 '로그인 이력' 에서 모든 계정의 이력을 아이디, 날짜, 결과로 걸러 본다.
- **지키는 것**: 웹에서는 지울 수 없고, 보관 기간(기본 1년, 12절)이 지나면 서버가 지운다.
- **켜고 끄기**: 관리자가 끌 수 있는 것은 '유저에게 자기 이력 보이기' 다. 기록 자체는 끄지 못하게 한다 (Claude 판단, 12절에서 확인). 끌 수 있으면 관리자 권한을 얻은 사람이 가장 먼저 끄게 되고, 사고가 났을 때 볼 것이 없어진다.

**그 밖**
- 두 기능은 사내 서버에서만 보인다. (나)는 그 PC 에서만 열리는 화면이라 지금 그대로 둔다 (같은 코드라 나중에 열 수 있다).
- **사내망으로 넓어지며 더 막는 것**
  - Host 와 Origin 검사를 127.0.0.1 고정에서 `server.json` 의 서버 이름·주소 목록으로 바꾼다. 모르는 이름으로 온 요청은 거절한다.
  - 로그인 잠금을 아이디 기준과 함께 **주소 기준**으로도 건다. 지금은 아이디만 세어서, 사내의 누군가가 관리자 아이디로 틀린 비밀번호를 계속 넣으면 관리자가 계속 잠긴다. 주소마다 10분에 10번 틀리면 그 주소를 10분 막고, 비밀번호 계산은 주소 제한을 통과한 요청만 한다. 같은 아이디가 잇따라 잠기면 잠금이 1분, 5분, 15분으로 길어진다.
  - 세션은 처음 로그인한 주소에서만 쓸 수 있다 (만드는 사람 판단으로 끌 수 있게).
  - 관리자 비밀번호는 10자 이상으로 올린다 (지금 8자). 보안 머리글에 HSTS 를 더한다.
- **여러 PC 고르기**: 일반 버전 웹의 `#pc-pick` 은 업체 정보에 PC 가 둘 이상이면 나온다. 서버가 `/api/company` 에 등록된 PC 들을 주고, 현황 구독과 명령과 실행 기록 창구가 PC 번호를 받게 하면 화면은 거의 그대로 돈다. 사용 중지된 PC 와 연결이 끊긴 PC 는 목록에 표시한다.
- **계정 역할**은 관리자와 유저(보기만) 둘 그대로다. PC 별 담당자 역할은 만들지 않는다 (12절).
- **새 카드** (환경설정, 관리자만): 'PC'(추가, 사용 중지, 지우기와 PC 마다의 버전, 마지막 연결 시각), '업데이트'(6.7), '서버'(서버 버전과 시각, 라이선스의 업체 이름과 자리 수, 인증서 만료일, 마지막 백업), '보안'(2단계 인증 범위, 유저에게 이력 보이기), '로그인 이력'. 화면은 지금 웹의 카드 모양을 따르고, 새 모양이 필요한 곳(2단계 등록과 번호 입력 화면 포함)은 시안을 먼저 보인다.
- **휴대폰 칸**은 지금 그대로다. QR 의 주소가 PC 주소에서 서버 주소로 바뀔 뿐이다.
- 숨기는 것은 (나)와 같다 (토큰, AI, 총괄 화면). [업데이트]·[되돌리기] 는 사내 서버에서 되살린다. 프리셋 옮기기는 맨 뒤 차례에서 되살린다.

### 6.7 업데이트 (가 방식)
- **PC 업데이트 파일** `AUTOPILOT_Update_<버전>.apu` 하나. 안의 모양은 지금 업데이트 사이트와 같다 (`releases/<버전>/manifest.json`, `manifest.sig`, `blobs/<지문>`). 새 도구 `tools/make_update_file.py` 가 배포 폴더와 업데이트 서명 열쇠로 만든다 (지금 `publish_release.py` 가 사이트 폴더에 올리던 것을 파일 하나로). 서명 열쇠를 쓰므로 만드는 것은 사용자다.
- **올리기**: 관리자가 '업데이트' 카드에서 파일을 올린다. 수백 MB 라 지금의 요청 본문 한도(64KB, 메모리에 다 읽음)와 따로, 디스크로 흘려 받는 올리기 창구를 둔다 (관리자만, 한 번에 하나, 크기 상한). 브라우저 올리기가 어려운 망을 위해 서버에 파일을 복사해 `autopilot-server update-add <파일>` 로 넣는 길도 둔다.
- **서버의 확인**: 올린 파일은 임시 자리에서 ① 압축 안의 이름이 정해진 꼴뿐인지, 푼 크기가 상한 안인지 ② 버전 목록의 서명이 실린 업데이트 공개 열쇠로 맞는지 ③ 스탠드얼론 버전의 목록인지 ④ 모든 파일의 지문과 크기가 목록과 같은지 본다. 다 맞아야 보관 자리로 옮긴다. 서버는 이 파일을 보관하고 내주기만 하고 실행하지 않는다.
- **PC 가 받기**: 관리자가 PC 별 [업데이트] 나 [모든 PC 업데이트] 를 누르면 지금의 `update` 명령이 그 PC 로 간다. 한 대에 먼저 넣어 보고 나머지에 넣는 순서를 화면 기본으로 한다. 에이전트는 받기 주소가 사내 서버의 8444 라는 것만 다르고 지금 일반 버전의 길을 그대로 탄다: 서명 확인 → 바뀐 파일만 받기 → 일이 없을 때까지 기다림 → 도우미가 바꾸기 → 3분 점검 → 문제면 되돌리기. **PC 는 서버를 믿지 않고 서명을 스스로 다시 확인한다.** 서버가 뚫려도 서명 없는 코드는 PC 에 들어가지 못한다.
- **되돌리기**는 지금처럼 그 PC 의 직전 버전 보관으로 한다 (`rollback` 명령). 서버는 최근 세 버전과 PC 들이 지금 쓰는 버전을 보관한다.
- **서버 자신의 업데이트**는 대시보드로 하지 않는다. 관리자가 새 서버 설치 파일을 서버에 복사해 root 로 `install.sh` 를 돌린다. 스크립트는 지금 깔린 서버의 확인 도구로 서명을 먼저 보고, 새 버전을 `releases/<버전>/` 에 풀고, 자료를 백업하고, `current` 링크를 바꿔 서비스를 다시 켠 뒤 상태를 확인한다. 실패하면 링크를 되돌린다. 대시보드로 하지 않는 까닭은 서비스 계정이 자기 프로그램을 바꿀 수 없어야 하기 때문이다. (Claude 판단)
- **순서 규칙**: 서버를 먼저 올리고 PC 를 나중에 올린다. 서버는 한 버전 앞의 에이전트 약속까지 받는다. 에이전트는 붙을 때 자기 버전과 약속 번호를 알리고, 맞지 않으면 화면에 '서버를 먼저 업데이트' 로 보인다.
- **나) 를 얹을 자리**: 나)는 '우리 업데이트 주소에서 `releases/<버전>/…` 과 `blobs/…` 를 받아 임시 자리에 두는 일' 하나를 더하는 것이다. 그 뒤의 확인, 보관, 나눠 주기는 같은 코드다. 받는 프로그램은 서버와 다른 서비스로 두어, 가) 서버 설치 파일에는 그 코드와 주소가 아예 들어가지 않게 한다 (8절의 주소 문자열 시험이 지킨다). 그 통로에 업데이트 말고 다른 것(라이선스 갱신, 상태 알림 등)을 실을지는 아직 답이 없다. 이 문서는 **업데이트만 싣는다**고 보고 자리만 둔다 (12절).

### 6.8 라이선스와 복사 막기
- **서버 라이선스**: 지금 라이선스 파일에 종류를 하나 더한다. 내용은 업체 이름과 코드, **서버 번호**, **자리 수**(등록할 수 있는 PC 수), 자리 서명 공개 열쇠, 그리고 모듈과 기능과 한도이고 우리 라이선스 열쇠로 서명한다. 발급 도구는 `tools/make_license.py` 에 서버용 인자를 더한다.
- **서버 번호**는 리눅스의 `/etc/machine-id` 를 그대로 쓰지 않고 우리 이름을 섞어 해시한 값이다. 설치 뒤 `autopilot-server request` 가 서버 번호와 자리 서명 공개 열쇠가 든 요청 파일을 만들고 (지금 `PC번호_확인.bat` 자리), 업체가 그것을 보내면 우리가 라이선스를 발급한다.
- **자리 증명서**: 서버는 PC 를 등록할 때 '이 업체의 이 PC(MachineGuid)는 자리를 받았다' 는 증명서를 자리 서명 열쇠로 서명해 준다. 등록된 PC 수가 자리 수에 이르면 더 등록하지 못한다.
- **PC 쪽 복사 막기**(`ap_guard`)는 사내 서버 연결일 때 이렇게 바뀐다. PC 번호 라이선스 대신 ① 우리가 서명한 서버 라이선스 사본 ② 그 라이선스의 자리 서명 공개 열쇠로 확인되는 자리 증명서 ③ 증명서의 PC 번호가 이 PC 의 MachineGuid 와 같은지를 본다. 서버에 묻지 않고 PC 안에서 확인하므로 서버가 꺼져 있어도 PROCESS·ACTOR·옵저버가 켜진다. 버전 목록 서명, 변조 감지, 컴파일 조각 확인은 지금과 같다.
- **기존 PC 라이선스와의 관계**: 둘은 서로 독립이다. (나)의 PC 번호 라이선스는 (나) PC 에서 지금 그대로 돌고, 사내 서버에 붙는 PC 는 새 PC 에 새로 설치해 등록 파일로 연결한다 (사용자 2026-11-24). (나)에서 (가)로 옮기는 절차와 도구는 만들지 않는다. 같은 라이선스 열쇠로 서명하므로 프로그램에 실린 공개 열쇠는 하나다.
- **한계** (보안 자료에 그대로 적는다): 서버의 root 를 가진 사람이 자리 서명 열쇠를 꺼내거나 서버 코드를 고쳐 자리 수 검사를 지나가는 것, VM 을 통째로 복제하는 것까지는 막지 못한다. 서버 코드는 처음에는 파이썬 파일 그대로 실리고 버전 목록 서명으로 고쳐졌는지만 본다. 더 단단히 하려면 라이선스에 PC 번호 목록까지 적는 방식(선택 칸으로 열어 둔다 - 있으면 PC 의 확인 조각이 목록에 자기 번호가 있는지도 본다)과 서버 확인 부분을 리눅스에서 컴파일하는 방식이 있다 (12절).

## 7. 휴대폰 인증번호

- 휴대폰은 PC 가 아니라 **서버의 8782** 에 붙는다. 약속 문서(`docs/phone-local-contract.md`)는 그대로 쓴다. 앱이 보기에 달라지는 것은 QR 의 주소뿐이다.
- 흐름: 관리자가 웹에서 [휴대폰 추가] → 서버가 QR(서버 주소, 포트, 짝 열쇠, 인증서 지문)을 보임 → 앱이 짝지음. ACTOR 가 2차 인증을 만나면 그 PC 의 중계 열쇠로 서버의 8444 에 요청을 연다 → 문자가 오면 휴대폰이 서버에 열린 요청을 묻고 번호를 보낸다 → ACTOR 가 서버에서 번호를 읽어 넣고 지운다. 번호는 서버 메모리에만 2분 있고 파일에 남지 않는다.
- (나)보다 나아지는 점: PC 주소가 바뀌어도 다시 짝짓지 않는다 (서버 주소는 고정). 휴대폰과 PC 가 서로 닿을 필요가 없고 휴대폰에서 서버 8782 로만 닿으면 된다. 휴대폰 한 대를 여러 PC 가 같이 쓴다.
- 여러 PC 가 같은 휴대폰을 쓰므로 **요청은 휴대폰마다 한 번에 하나**다. 다른 PC 의 요청이 열려 있으면 서버가 거절하고, ACTOR 는 지금 일반 버전처럼 그 요청이 끝나기를 기다렸다 연다 (`otp_relay.PhoneRelay.open` 에 이미 있는 동작). 번호 읽기와 지우기도 그 요청을 연 PC 만 한다. 이 검사는 지금 로컬 서버에 없으므로 더한다 (13절 6번).
- 리눅스에서는 서비스가 방화벽을 바꾸지 못한다. 8782 규칙은 설치 때 관리자가 넣고 (휴대폰 와이파이 대역만), 서버는 지금처럼 짝지은 휴대폰이 있거나 짝짓는 중일 때만 그 포트를 듣는다.
- 안 될 때는 어제와 같다. 2분 안에 번호가 없으면 그 PC 의 Edge 칸에 사람이 넣기를 5분 기다리고, 그래도 없으면 그 사이트만 실패한다.
- 이 절의 휴대폰은 쇼핑몰의 문자 인증번호를 넘기는 용도이고, 6.6 의 2단계 인증(대시보드 로그인용 인증 앱)과는 다른 것이다. 같은 휴대폰에 둘 다 있어도 서로 상관없다.

## 8. 바깥 연결 0 지키기

- **서버**: 가) 에서 서버 코드는 연결을 **여는 코드가 없다** (듣기만 한다). 이것을 세 가지로 지킨다. ① 서버에 실리는 우리 코드와 웹 파일에 Firebase·Google·Anthropic·우리 사이트 주소 문자열이 없는지, 서버 모듈이 바깥으로 연결하는 라이브러리를 불러오지 않는지 보는 시험 (지금 `tests/test_standalone_offline.py` 를 서버 설치 파일로 넓힌다). ② systemd 의 주소 제한과 방화벽의 나가는 규칙. ③ NT 에서 나가는 패킷을 막고 기록한 채 전체 시나리오를 돌려 서버가 사내 대역 밖으로 보내려 한 패킷이 0 인지 확인.
- **PC**: 어제 8절 그대로이고 허용 대상에 '등록된 사내 서버 주소' 하나가 더해진다. PC 는 사설 대역이 아닌 서버 주소로는 등록하지 않는다. 샌드박스의 hosts 차단 목록과 소켓 연결 대상 시험을 사내 서버 연결로도 돌린다.
- **브라우저**: 업체 웹은 지금처럼 같은 출처의 파일과 `/api` 만 부른다 (CSP `default-src 'self'`, 글꼴·아이콘은 실린 사본). 2단계 인증의 QR 도 화면 안에서 그린다 (바깥의 QR 서비스를 부르지 않는다).
- 서버는 이름 풀이(DNS)를 하지 않는다. 듣는 주소와 QR 에 싣는 주소는 `server.json` 에서 읽는다.
- '바깥 연결 0' 의 뜻은 어제 8절과 같다 (프로그램이 스스로 여는 연결 기준, Edge 안의 쇼핑몰 화면이 부르는 것은 쇼핑몰의 일부).

## 9. NT 시험 환경

- **무엇**: 개발 PC 가 아닌 **새 PC** 의 VMware 에 리눅스 VM "NT" 하나를 둔다 (사용자 2026-11-24).
- **배포판**: **사용자가 깐 것을 따른다.** 업체 서버와 같은 배포판이 가장 좋다. 업체 것을 모를 때는 Ubuntu 24.04 LTS 나 Rocky Linux 9 어느 쪽이어도 된다. 설치 스크립트는 두 계열을 다 다룬다 (Ubuntu 계열은 ufw 와 AppArmor, RHEL 계열은 firewalld 와 SELinux). 업체 서버가 NT 와 다른 계열로 밝혀지면 그 배포판의 VM 을 하나 더 만들어 설치와 방화벽 부분을 다시 본다.
- **자원**: CPU 2개, 메모리 4GB, 디스크 40GB (업데이트 보관에 여유를 둔다).
- **나눠 맡기**: 사용자가 손으로 하는 것은 VMware 와 리눅스 설치, 주소 고정, SSH 켜기, 스냅숏 찍기와 되돌리기다. VM 안의 설치와 시험은 Claude 가 개발 PC 에서 SSH 로 한다 (`tools/nt_test.py` 가 서버 설치 파일을 넣고, 명령을 돌리고, 기록을 가져온다). 개발 PC 와 NT 가 같은 사내망에서 서로 닿을 때의 이야기다. 닿지 않으면 명령을 적은 스크립트 파일 하나를 사용자에게 건네고, 사용자가 NT 에서 돌린 뒤 결과 파일을 돌려주는 방식으로 한다. SSH 열쇠와 NT 주소는 저장소 밖 파일에 둔다. SSH 허용 여부는 12절에 남긴다.
- **망**: 브리지 방식으로 사무실 망의 주소를 하나 고정해 준다. 그래야 사무실의 다른 PC 와 와이파이의 휴대폰이 실제 업체처럼 붙는다. 공유기에서 이 주소로 포트를 넘기지 않는다 ('우선 사내에서만').
- **닫힌 망 흉내**: VM 방화벽에서 나가는 연결을 사무실 대역 말고 모두 막고 막힌 패킷을 기록한다. 우리 서버 설치 파일만으로 설치가 끝나는지 보는 것이 첫 시험이다. 프록시 확인에 쓸 nginx 처럼 인터넷이 있어야 깔 수 있는 것은 망을 닫기 전에 사용자가 깔아 둔다.
- **스냅숏**: 운영체제만 깐 상태를 '깨끗한 설치' 로 찍어 두고, 설치 시험마다 그 상태로 되돌린다 (윈도우 샌드박스가 매번 새것인 것과 같은 구실). 되돌리기는 사용자 손이 필요하므로 설치 시험은 한 번에 몰아서 한다.
- **시험용 라이선스**: NT 에는 시험용 빌드(시험 열쇠, 화면 맨 위 '시험용 빌드' 띠)와 시험 라이선스(자리 10)를 쓴다. 정식 열쇠 라이선스로 한 번 도는 것은 고객 납품 직전에 사용자가 한다.
- **윈도우 PC 쪽과 맞추기**: 개발 PC 의 윈도우 샌드박스에 스탠드얼론을 깔고 NT 에 등록하는 시험을 `tools/sandbox_test.py` 에 더한다 (설치 → 등록 → 현황 → 가짜 실행 명령 → 기록 → 서버에서 업데이트 받기 → 되돌리기). 샌드박스는 개발 PC 를 거쳐 나가므로 NT 에는 개발 PC 주소로 보인다. 그래서 여러 PC 를 가르는 시험은 가짜 에이전트 여러 개로 하고, 실제 PC 두 대는 붙일 새 PC 로 사람이 확인한다.

- **스탠드얼론 보안 자료**
  - 웹 인증 다섯 가지를 표로 답한다. 2단계 인증은 '인증 앱 방식, 관리자 계정은 기본 필수, 업체 관리자가 범위를 정함', 로그인 이력은 '화면으로 조회, 기록은 끌 수 없음, 보관 기간' 으로 적는다. 2단계를 끌 수 있다는 것과 끈 일이 기록에 남는다는 것도 함께 적는다.
  - 새로 밝힐 것: 2단계 비밀 값이 서버에 저장된다는 것과 읽을 수 있는 사람, 잃었을 때의 복구 절차와 그 권한(서버 root), 로그인 이력에 남는 항목(아이디, 주소, 브라우저 종류).
  - 통신 구간 표(브라우저와 서버, PC 와 서버, 휴대폰과 서버 - 각각 암호화와 서로 확인하는 방법), 프록시를 둘 때 달라지는 구간과 주소를 믿는 조건.
  - 서버에 저장되는 것과 읽을 수 있는 사람, 서버로 오지 않는 것(쇼핑몰과 ERPia 와 엑셀의 비밀번호), 사내 대역만 받는 세 겹, PC 등록과 사용 중지, 업데이트 파일을 서버와 PC 가 각각 확인하는 것, PC 신뢰 저장소에 넣는 인증 기관과 이름 제한, 서버 계정 권한과 systemd 보호 설정, 백업 파일에 든 것, 라이선스와 그 한계(6.8), 바깥 연결 0 을 확인한 방법.
  - 법 해석은 단정하지 않는다. 업체가 정해지면 그 업체의 보안 의견 항목 순서로 다시 맞춘다.
- 저장 위치와 작성자 표기는 어제와 같다 (`D:\AX_보고용 문서 모음`, "작성 : 원제로소프트").

## 13. 지금 코드에서 걸리는 곳 (읽으며 찾은 것)

1. `local_store.Client` 는 `http` 와 127.0.0.1 만 받는다. 또 요청 서명의 시각에 서버와의 시계 차이를 쓰지 않는다 (`_offset` 은 `server_now` 에만 쓴다). 서버와 PC 가 갈라지면 PC 시계가 60초 넘게 틀린 순간 모든 요청이 거절된다.
2. `Store` 는 쓰기 한 번마다 나무 전체를 복사하고 파일 전체를 다시 써서 fsync 한다. 메모리에만 두는 현황이 바뀔 때도 저장이 돈다. PC 10대까지는 구조를 그대로 두되 현황만 바뀐 쓰기의 파일 저장은 건너뛰게 한다 (6.5).
3. `local_web.Web` 은 PC 하나에 고정돼 있다 (`_live`, `_cmds`, `_runs` 의 PC 검사, `_company` 가 서버의 컴퓨터 이름을 PC 이름으로 줌). 연결 상한도 PC 한 대 기준이다 (`MAX_CONN` 64, `MAX_STREAMS` 16).
4. 로그인 잠금이 아이디 기준뿐이고, 비밀번호 확인이 잠금 하나(`_login_lock`) 안에서 31만 번 해시를 돈다. 사내망에서는 관리자 아이디를 계속 잠그거나 로그인을 줄 세우는 데 쓰일 수 있다.
5. 요청 본문을 메모리에 다 읽는다 (`Handler._read`, 4MB 상한). 업데이트 파일은 다른 길이 필요하다.
6. 인증번호 요청을 여는 자리에 '다른 PC 의 요청이 열려 있으면 거절' 이 없다. PC 가 하나라 필요 없었지만 여러 PC 에서는 뒤에 온 PC 가 앞 요청을 덮는다.
7. 자동 업데이트가 스탠드얼론에서 통째로 빠져 있다. `update_helper.py` 는 스탠드얼론 빌드에 실리지 않고, 그 안의 예약 작업 이름, 잠금 이름, 제거 등록 키가 일반 버전 값으로 박혀 있다. 또 스탠드얼론의 `manifest.sig` 는 버전 목록에 없이 설치 파일만 싣는데 `ap_guard` 는 프로그램 폴더의 그 파일로 서명을 본다. 도우미가 버전 목록과 서명 파일을 함께 바꾸지 않으면 **첫 자동 업데이트 직후 PROCESS·ACTOR·옵저버가 모두 '서명을 확인하지 못했습니다' 로 막힌다.** 도우미가 쓰는 파일 목록(`rpa_update.RUNNER_FILES`)에 새 모듈을 빠뜨려 업데이트가 실패한 적도 있다.
8. `local_cert` 는 윈도우의 `libcrypto-3.dll` 을 이름으로 부른다. 리눅스 내장 파이썬은 OpenSSL 을 안에 넣어 빌드한 것이라 같은 방법으로 부를 수 없을 수 있다.
9. 윈도우 전용 코드가 서버 파일에 섞여 있다. 파일 잠그기(`icacls`), 휴대폰 포트의 방화벽과 주소 찾기(`netsh`, PowerShell), PC 번호(`winreg`), 자료 폴더(`ProgramData`), 창 없이 띄우기 깃발(리눅스에서는 오류). 듣는 소켓의 `allow_reuse_address = False` 는 리눅스에서 서비스를 다시 켤 때 잠깐 '주소 사용 중' 을 낼 수 있다.
10. `ap_guard` 와 `edition` 은 PC 번호 라이선스 하나만 안다. `agent.py` 는 `standalone` 이면 업데이트와 프리셋 옮기기 명령을 한꺼번에 거절한다. 연결 방식별로 갈라야 한다.
11. Host 와 Origin 검사가 127.0.0.1 로 박혀 있다 (`local_server.local_host`, `local_web.Web._api`). 보낸 쪽 주소는 소켓의 주소만 본다. 프록시 뒤에 서면 모든 사용자가 프록시 주소 하나로 보인다.
12. `local_web.Accounts` 는 비밀번호를 바꾸거나 다시 정할 때 계정 기록을 정해진 칸으로 새로 만든다 (`_record`). 2단계 인증 칸을 그냥 더하면 **비밀번호를 바꾸는 순간 2단계 설정이 소리 없이 지워진다.** 계정 파일 버전을 올리면서 이 자리를 같이 고친다.
13. 로그인 기록은 지금 서버 기록 파일에 글 한 줄로만 남고(1MB 가 넘으면 앞 것 하나만 남기고 넘어간다), 보낸 쪽 주소가 없다. 로그인 이력 화면은 따로 저장해야 한다.

## 14. 차례 (계획 때 나눌 단위)

앞 단위가 만든 이름을 뒤 단위가 쓰므로 계획은 앞 것이 끝난 뒤에 자세히 쓴다 (어제와 같다). 각 단위를 시작하기 전에 develop 을 합쳐 받는다. 새 PC 에만 설치하므로 (나)나 일반 버전에서 옮겨 오는 단위는 없다.

| # | 단위 | 끝나면 되는 것 | 시험하는 곳 |
|---|---|---|---|
| ① | 서버 넓히기 | 배치 설정, 여러 PC 저장소와 자리 검사, PC 등록부, `ap2` 서명, 시계 맞추기, 인증번호 요청 차례, 현황만 바뀐 쓰기의 저장 건너뛰기 (13절 1, 2, 3, 6) | 개발 PC (가짜 PC 여러 개, TLS 없이) |
| ② | 사내망 창구 | 세 포트의 TLS, 인증 기관 만들기, 허용 대역과 Host 와 Origin 검사, 믿을 프록시 주소로 보낸 쪽 주소 읽기, 주소별 제한과 로그인 잠금, 인증 기관만 믿는 클라이언트 (13절 4, 8, 11) | 개발 PC, WSL |
| ③ | 웹 인증 보강 | 계정 파일 버전 2, 2단계 인증(등록, 로그인, 복구 번호, 관리자가 풀어 주기), 로그인 이력 저장과 조회 창구, '보안' 설정 (13절 12, 13). 화면은 ⑥ 에서 | 개발 PC |
| ④ | 리눅스에 싣기 | 내장 리눅스 파이썬, 서버 설치 파일, `install.sh`, systemd, 폴더 권한, 기록, 백업, 관리 명령(`admin-reset` 포함), 서버 라이선스와 서버 번호 (13절 9) | WSL → **NT 첫 사용** (깨끗한 스냅숏에 설치, 재부팅, 나가는 연결 막고 확인). 끝에 **nginx 를 앞에 세워 로그인과 현황 구독이 되는지 먼저 본다** - 업체 IT 와 서버 구조를 이야기할 근거 |
| ⑤ | PC 쪽 | 연결 방식, 설정 창과 설치 마법사의 등록, 자리 증명서와 `ap_guard`, 감독이 로컬 서버를 띄우지 않음, 빌드 (13절 10) | 개발 PC, 샌드박스 + NT |
| ⑥ | 업체 웹 | 여러 PC 고르기, 'PC'·'서버'·'보안'·'로그인 이력' 카드, 2단계 등록과 번호 입력 화면 (새 화면은 시안 먼저), 사내 서버용 화면 시험 | 개발 PC, NT 에 사무실 PC 로 접속 |
| ⑦ | 업데이트 가) | 업데이트 파일 만들기, 올리기와 확인과 보관, PC 가 받아 도우미로 바꾸고 되돌리기, 서버 자신의 업데이트 (13절 5, 7) | 개발 PC, 샌드박스 + NT |
| ⑧ | 휴대폰 | 서버의 인증번호 창구, 리눅스 방화벽 안내, 흉내 시험. 실제 휴대폰은 앱이 나온 뒤 | 개발 PC, NT |
| ⑨ | 전체 확인 | NT 에서 처음부터 끝까지, 바깥 연결 0, 가짜 에이전트 10개 부하(10절 기준), nginx 를 앞에 세운 두 모양 전체(업데이트 올리기 포함), 붙일 새 PC 두 대로 사람 확인 | NT |
| ⑩ | 문서 | 설치 안내서, 사용설명서, 보안 자료 (11절) | - |
| ⑪ | 나중 | 프리셋 옮기기 되살리기 (무엇이 서버를 지나가는지 그 계획에서 다시 확인), 나) 통로, 서버 확인 부분 컴파일 | - |

실제 업체 서버에는 ⑨ 가 NT 에서 통과한 뒤에 들어간다. ③ 은 리눅스가 필요 없어 ④ 와 순서를 바꾸거나 함께 가도 된다.
